# CLAUDE.md — контекст проекта

## Что это за проект
Подготовка к алгоритмической секции собеседований Java-разработчика.
Цель пользователя (Lela): пройти алгосекцию, не закапываясь в теорию надолго.
Рынок РФ/СНГ, собеседования на русском. Референс-компания — Т-Банк (бывш. Тинькофф).
Грейд — Senior. Главный риск: усидчивости на долгую учёбу может не хватить →
упор на минимально достаточный объём и быстрый PASS/FAIL фидбэк.

## Рабочий журнал (память проекта)
Журнальные файлы лежат в папке `journal/` — на старте сессии заглядывать туда:
- `journal/progress.md` — что уже сделано (только дописывать в конец).
- `journal/todo.md` — что осталось (статусы правим на месте).
- `journal/notes.md` — справочник, метод обучения, техзаметки.
Этот `CLAUDE.md` — точка входа, остаётся в корне и читается первым.

## Как мы работаем

### Правки только по просьбе
Вопрос — это вопрос, а не задание. Если Lela спрашивает «почему так», «а можно
иначе», «что это значит» — надо ОТВЕТИТЬ, а правку в файл предложить отдельно
и внести после подтверждения. Даже когда правка кажется очевидной и мелкой.

Так уже ловилось дважды. Один раз при сборке PDF я нашла в `.md` типографский
минус и молча его поправила — задача была про PDF, исходник трогать не просили.
Правило шире: границы задачи задаёт Lela, а не моё представление о том,
что «заодно стоило бы».

Исключение — когда правка прямо следует из уже данной команды. Попросили
переименовать метод: заодно чиню все места, где он упоминается, и не спрашиваю
про каждое.

### Предлагать, а не молчать
Правило выше запрещает молча ПРАВИТЬ, но не запрещает ПРЕДЛАГАТЬ. Если по ходу
задачи видно, что та же проблема есть рядом, — сказать об этом одной строкой
в конце ответа.

Так вышло с визуализациями блока 4: перевёрстку первой сделали по просьбе,
а вторая осталась в старом виде, и Lela спросила «почему не предложила».
Ответ «правки только по просьбе» тут не годится: предложение — это не правка.

### Язык изложения
Тексты читаются вслух и разбираются медленно, поэтому язык проверяется
отдельно от содержания.

- НИКАКОГО ЖАРГОНА. Слова «прогон», «отработать», «накидать», «зарезать»
  в разборах не место. Вместо «за весь прогон» — «за всё время работы
  алгоритма», вместо «таблица прогона» — «разбор по шагам».
- КОНСТРУКЦИЯ ДОЛЖНА БЫТЬ РУССКОЙ. Перед тем как оставить фразу, проверить,
  говорят ли так вообще. Поймано у меня: «характеристика, обновляемая НА
  разницу» (так не говорят, и непонятно, о какой разнице речь) и «утверждение
  остаётся истинным, хотя данные ПОД НИМ меняются» (данные не могут быть
  «под» утверждением). Правильно — прямо и буквально: «прибавить вошедший
  элемент и вычесть вышедший», «хотя сами переменные при этом меняются».
- МЕТАФОРА ТОЛЬКО РАБОЧАЯ. Если образ не выдерживает буквального прочтения,
  он мешает, а не помогает.
- НЕЗНАКОМЫЙ ТЕРМИН — В СЛОВАРИК. Появилось слово, которое Lela встречает
  впервые (инвариант, амортизация, фолбэк), — оно идёт в `docs/glossary.md`,
  а в тексте раскрывается одной фразой.
- ЧИСЛА В ТЕКСТЕ СВЕРЯТЬ С КОДОМ. Фразы вида «переменная используется трижды»,
  «сравнивается дважды» — это утверждения о коде, и они проверяются подсчётом.
  У меня дважды оказывались неверными.

### Порядок изложения в разборе
Сначала показать решение, потом объяснять его части. Порядок такой: идея
словами → код → таблица «Что делает каждая переменная» → разборы ловушек.

Если в классе несколько методов, КАЖДЫЙ описывается словами, а не просто
показывается кодом. Ошибка, которую поймала Lela: таблица переменных для
варианта с прыжком стояла сразу после таблицы для варианта с множеством —
то есть до того, как сам метод был где-либо описан, и читать её было не по чему.

### Не плодить сущности
Новое пояснение по умолчанию идёт РАЗДЕЛОМ в существующий файл, а не отдельным
файлом. Отдельный файл заводится, только когда Lela сама об этом просит.

Так был удалён `docs/SubstringVsSubsequence.md`: разбор терминов «подстрока»
и «подпоследовательность» оказался разделом внутри разбора задачи, где эта
путаница и всплыла.

### Цикл работы над задачей
Порядок такой: класс в `src/` → разбор в `docs/problems/` → тесты в `main()`
→ компиляция и прогон на локальной JDK → визуализация в `docs/visualizations/`
→ записи в `journal/`. Ни один шаг не пропускается, разрешения на визуализацию
спрашивать не надо.

Статус `[x]` в `journal/todo.md` ставится, только когда Lela ЗАКОНЧИЛА
РАЗБИРАТЬ задачу, а не когда код написан и тесты зелёные. Написанный
и прогнанный код — это `[~]`. Одна задача может висеть в `[~]` несколько дней,
это нормально.

### Git
- Коммитим и пушим ТОЛЬКО по команде. Слова «пуш», «хрюш», «пуш-хрюш»,
  «запушь» означают одно и то же: закоммить всё и отправить.
- Сообщения коммитов — на английском, тело развёрнутое: что изменилось
  и почему, включая пойманные ошибки. Всё остальное в проекте на русском.
- Ветку не переключаем, работаем на текущей — см. скилл
  `git-branch-discipline`.
- Перед коммитом прогнать затронутые классы и убедиться, что тесты зелёные.
- Если за время работы накопились изменения ПО РАЗНЫМ ТЕМАМ, разносить их
  по отдельным коммитам, а не сваливать в один. Когда тема размазана по файлам,
  которые правились и в другой теме (CLAUDE.md, journal, разбор задачи),
  порядок такой: временно откатить правки второй темы, закоммитить первую,
  вернуть откаченное и закоммитить вторую.
- ЗАКОММЕНТИРОВАННЫЕ ТЕСТЫ — это отладочный остаток, а не решение. Увидев
  такое, сказать об этом прямо и предложить вернуть; не подстраивать под них
  текст разбора и не сужать формулировки.

## Структура проекта
- `algo-prep-plan.md` — общий план: ядро из 6 блоков паттернов, план A (1–2 недели)
  и план B (месяц), задачи с ссылками на LeetCode, опорные решения на Java.
  Порядок задач ВНУТРИ блока плану не подчиняется: берём от простого к сложному,
  по логике обучения. Так блок 4 начали с MaxAverageSubarray (окно фиксированной
  ширины), а не с задачи 3, где сразу и переменная ширина, и состояние.
- `src/blockNN_<тема>/` — по пакету на блок; каждая задача = отдельный класс.
  Реализован блок 1: `src/block01_arrays_twopointers/`.
- `src/demo/` — классы, которые НЕ являются задачей из блока: иллюстрации
  к справочникам из `docs/java/` и `docs/datastructures/`. Оформляются как
  обычные классы с `main()` и проверками через `check`, но в списке задач блока
  не числятся. В Javadoc — ссылка на справочник, к которому относится пример.
- `tools/` — вспомогательные скрипты, не относящиеся к задачам.
  `tts_pdf.py` — сборка PDF из `.md` для чтения вслух, см. раздел про PDF ниже.
- `.gitignore` — игнорит `*.tar.gz` (JDK для песочницы), out/target и `.idea/`.
- `rag/mcdowell-cracking-coding-interview.md` — RAG-источник: полный текст книги
  Г. Лакман Макдауэлл «Карьера программиста» (Cracking the Coding Interview,
  6-е изд., СПб.: Питер, 2021), OCR из исходного .docx. Использовать как
  справочник по задачам/теории при подготовке.
  ОРИГИНАЛ В PDF лежит у Lela на машине, вне примонтированной папки:
  `C:\Users\Ola\Documents\Лакман Макдауэлл Г. - Карьера программиста
  (Библиотека программиста) - 2021\...pdf`. Сверяться с ним, когда RAG вызывает
  сомнения: OCR местами портит текст, а числовые примеры вообще надо
  пересчитывать (в задаче 17.10 разборный массив напечатан двумя способами,
  и версии не совпадают — это опечатка самой книги).
  Рецепт сверки: на машине есть `pdftotext` из состава Git for Windows
  (`C:\Program Files\Git\mingw64\bin\pdftotext.exe`) и Python 3.14. Извлечь
  текст `pdftotext -enc UTF-8 -eol unix <pdf> <txt>`, разбить питоном по `\f`
  на страницы и искать. Нумерация страниц PDF совпадает с печатной.
- `docs/heuristics.md` — шпаргалка пользователя: общие приёмы решения задач
  (как придумать условие цикла и т.п.), каждый приём с примером из проекта.
  При разборе каждой задачи: (1) явно ссылаться на применимые пункты шпаргалки
  («это приём N из heuristics.md»); (2) дописывать новую задачу как пример
  к существующему приёму; (3) если всплыл новый общий приём — добавлять его
  отдельным пунктом.
- `docs/glossary.md` — словарик терминов, которые всплывают в разборах и на
  собеседовании (инвариант, амортизация, фолбэк, in-place, устойчивость…).
  У каждого термина: что значит, откуда слово взялось и где встречается
  в проекте, со ссылками на конкретные разборы. Пополняется по мере работы:
  если в тексте появился термин, который Lela встречает впервые, ему место
  здесь, а не в очередной сноске внутри разбора.
- `docs/datastructures/` — справочники по структурам данных стандартной библиотеки
  (`Queue.md`, `Deque.md`, …) в объёме собеседования. Это НЕ разбор задач: здесь
  инструменты, в `docs/problems/` — задачи. Правила: факты о поведении проверять
  запуском на локальной JDK и приводить фактический вывод; детали внутреннего
  устройства сверять с исходниками из `src.zip` (лежит в `lib/` у JDK), а не по
  памяти — часть общеизвестных фактов устарела. Иллюстрации — отдельными файлами
  `.svg` в `docs/datastructures/img/`, вставка через `![подпись](img/файл.svg)`
  (инлайновый SVG внутри markdown на GitHub не рендерится). Каждый справочник
  заканчивается разделом «Типичные вопросы на собеседовании».
- `docs/java/` — справочники по механике самого языка и JVM (переменные и память,
  приведение типов, равенство объектов). Границы: `docs/problems/` — задачи,
  `docs/datastructures/` — типы стандартной библиотеки, `docs/java/` — язык.
  Правила те же, что у datastructures: утверждения проверять запуском, байткод
  смотреть через `javap -c`, иллюстрации отдельными `.svg` в `img/`.
- `docs/visualizations/block NN_<тема>/` — визуализации и вспомогательные
  материалы (HTML, схемы). Зеркалит структуру `src/` по блокам; имя файла =
  имя задачи (напр. `docs/visualizations/block01_arrays_twopointers/TwoSumSorted.html`).
  Не-Java файлы держим здесь, а НЕ в `src/` (это Sources Root — только Java).
  ВИЗУАЛИЗАЦИЮ ДЕЛАТЬ СРАЗУ, не спрашивая разрешения. Она часть стандартного
  цикла задачи, а не отдельная опция: класс → .md → тесты → компиляция и прогон
  → визуализация. Спрашивать «делать ли визуализацию» не надо.
  В .html НЕ дублировать объяснения из .md. Разбор задачи — идея, ловушки,
  сложность, «на что смотреть» — живёт в `docs/problems/`, и повторять его
  блоком текста под визуализацией не надо. В .html допустим только текст,
  который объясняет САМУ КАРТИНКУ и без неё бессмысленен: легенда, что
  означает элемент схемы, расшифровка обозначений. Пример допустимого —
  блок в `TwoSum.html`, поясняющий, что на схеме `table`, бакет и узел
  (в `TwoSum.md` внутреннего устройства HashMap нет вовсе).

## Соглашения по коду (важно соблюдать в каждом классе)
- Один класс на задачу, имя класса описательное.
- Полное условие задачи — отдельным файлом `docs/problems/blockNN_<тема>/<Класс>.md`
  (литкодовский формат: условие → примеры → ограничения → идея → свойства решения,
  своими словами, не копия текста LeetCode). Структура зеркалит `src/`.
- В каждом разборе — раздел «Что делает каждая переменная»: таблица
  «переменная → что хранит → зачем нужна», по строке на КАЖДУЮ переменную
  решения, включая входные параметры и промежуточные структуры (счётчики,
  множества, карты, вспомогательные массивы). Не «в целом решение делает то-то»,
  а назначение каждой сущности по отдельности: почему она вообще заведена,
  какую роль играет в алгоритме и что сломается без неё.
  Причина от Lela: общая картина после разбора складывается, а на деталях
  начинаются провалы — непонятно, за что отвечает конкретный указатель или
  конкретная карта.
  Пояснения про имена (почему названо так, а не иначе) идут туда же, но одной
  строкой; развёрнутый разбор ловушки — отдельным разделом ниже.
- Вместо раздела «Сложность» в каждом разборе идёт раздел «Свойства решения»
  (или «Свойства решений», если методов несколько): таблица, где время и память —
  лишь первые строки. Остальные строки подбираются ПО ЗАДАЧЕ, единого шаблона нет.
  Ходовой набор: время в худшем и лучшем случае, память, число проходов по входу,
  ранний выход, изменяет ли вход, требования к входу, работа на потоке,
  детерминированность, завершаемость, устойчивость к деградации, устойчивость
  (stability) для сортировок, поведение на вырожденных входах.
  Правило то же, что и везде: утверждение в таблице либо следует из кода, либо
  подтверждено тестом. Если свойство не реализовано, а лишь возможно, так
  и писать («в коде его нет, добавить можно»).
- В каждом файле `docs/problems` СРАЗУ под английским заголовком (H1) — строка с
  переводом названия на русский, курсивом `*...*`: сначала общепринятый перевод,
  а в скобках дословный с глаголом, если в оригинале глагол. Примеры:
  `# 88. Merge Sorted Array` → `*Слияние отсортированных массивов (дословно: слить
  отсортированные массивы)*`; `# 1. Two Sum` → `*Сумма двух чисел*` (глагола в
  названии нет — скобки не нужны). Файлы-паттерны с уже русским заголовком не трогаем.
- У КАЖДОГО блока — свой обзорный файл `docs/problems/blockNN_<тема>/Pattern_<Имя>.md`
  (напр. `Pattern_TwoPointers.md`, `Pattern_HashMap.md`, `Pattern_StringsAndStack.md`).
  Это НЕ разбор задачи и не сборник выжимок из разборов. Файл отвечает ровно
  на два вопроса: почему задачи блока собраны вместе и чем этот блок отличается
  от соседних, с которыми его путают. Разделы: что объединяет задачи блока →
  подвиды приёма (по фразе на каждый, с опорной задачей) → отличие от соседнего
  блока → как распознать, что нужен именно этот приём. Если блок объединён
  не приёмом, а типом данных, так и писать.
  ЗАПРЕЩЕНО дублировать сюда содержимое разборов: код решений, разбор ловушек,
  объяснение имён переменных, трассировки. Всё это живёт в `<Класс>.md`, а здесь
  максимум ссылка. Требование Lela, дословно: «Суть общего маркдауна — пояснить
  в целом, почему блоки задач сгруппированы именно так»; остальное было
  «просто накидано то же самое, что и в конкретных задачах».
  Признак, что файл поехал не туда: в нём появился блок кода конкретного
  решения, раздел «частые ловушки» с разбором, имена переменных или таблица
  прогона по шагам.
- В начале класса — Javadoc /** ... */ с КРАТКИМ описанием (задача в 2-4 строки,
  паттерн, сложность) и ссылкой на .md через @see. Полную простыню в комментарий
  не дублируем — она в .md.
- Комментарий не должен быть длиннее метода, который он поясняет. Разбор идеи,
  происхождение имён, обоснование краевых случаев — всё это живёт в `.md`.
  В коде остаётся только то, что из самого кода не видно. Ориентир: если
  комментарий пересказывает раздел `.md`, его надо сократить до одной строки
  со ссылкой.
- Решение — чистая static-функция: вход → выход, без чтения с консоли.
- ПАРАМЕТРЫ ПРОВЕРЯТЬ СРАЗУ, охранным условием в начале метода. Если по коду
  непонятно, что делать с каким-то входом (пустой массив, null, отрицательная
  длина), не пробрасывать его вглубь и не надеяться, что внутренний метод
  как-нибудь справится — проверить на входе и бросить исключение,
  обычно `IllegalArgumentException` или `NullPointerException`.
  Смысл в том, чтобы корректность была ПО ЗАМЫСЛУ, а не по совпадению:
  «оно и так не падает» ломается при первой же правке соседнего метода.
  ОГРАНИЧЕНИЕ: только если это не противоречит условию задачи. Когда LeetCode
  требует вернуть специальное значение (`-1`, `null`, пустой список),
  возвращаем его — это контракт, а не ошибка. И когда ограничения задачи
  вход исключают (например `1 <= nums.length`), проверку можно не ставить
  вовсе, но тогда написать об этом в комментарии, чтобы отсутствие проверки
  читалось как решение, а не как недосмотр.
- Тесты прямо в main() через приватный helper check(boolean, String),
  печатающий "PASS — описание" / "FAIL — описание". Без JUnit и сборщиков.
- Тесты для алгоритмов должны покрывать ВСЕ ветви условных переходов. Перед
  написанием тестов ЯВНО выпиши список всех ветвей метода и пройди по нему пункт
  за пунктом, убедившись, что на каждую есть тест. Не забудь ни одну из групп:
  - каждая ветка if / else if / else;
  - КАЖДАЯ точка return, включая финальный ФОЛБЭК — тот, что срабатывает, когда
    цикл завершился, ничего не найдя (напр. `return {-1,-1}` / «не найдено» / null).
    Это самая частая пропущенная ветка — проверять её ОБЯЗАТЕЛЬНО и всегда отдельным
    тестом;
  - выход из цикла по ложному условию (while/for не начался или завершился);
  - граничные случаи: пустой вход, один элемент;
  - срабатывание защитных проверок (напр. индекс уходит за границу).
  Правило-памятка: у каждого `return` в методе — свой тест.
- Комментарии и описания тестов — на русском.
- Стиль комментариев: многострочные — одним блоком /* */, с заглавной буквы.
- Скобки у тел управляющих конструкций — см. скилл `java-code-braces-for-control-bodies`.
- Именование переменных и параметров (раскрывающие имена, без однобуквенных) —
  см. скилл `java-meaningful-names`. Три добавки от Lela:
  прилагательное без существительного именем быть не может (`majority` — что
  именно мажоритарное? переменная хранит кандидата, значит `majorityCandidate`);
  и при переводе имени с русского проверять не только словарное соответствие,
  но и ассоциации слова в предметной области. Так `outstanding` — самый дословный
  перевод слова «непогашенный», но в задаче про выборы `outstanding votes`
  по-английски значит «ещё не подсчитанные голоса», то есть ложный друг.
  И третья: если переменную цикла МОЖНО назвать осмысленно — назвать. Нейтральные
  `currentIndex` / `readIndex` годятся, только когда у индекса нет роли, кроме
  «идём по массиву». Как только роль есть, имя обязано её назвать. В
  `MaxAverageSubarray` индекс второго цикла — правая граница окна, поэтому он
  `windowEnd`, а не `currentIndex`; вычитаемый индекс — левая граница, поэтому
  `windowStart`, а не выражение `currentIndex - k` по месту. После такого
  переименования комментарий, объясняющий смысл индексов, становится не нужен:
  его пересказывают сами имена.
- ИСКЛЮЧЕНИЕ из правила именования: код, воспроизведённый из книги Макдауэлл
  ДОСЛОВНО, переносится один в один, включая однобуквенные имена вроде `n`
  и `x`, и в комментарии это оговаривается. Но дословный перенос — не цель
  сам по себе: если из книги берётся только идея, код пишем своими именами.
  Так вышло с `MajorityElement` — сначала тело скопировали буквально, потом
  переименовали переменные под читаемость, и книжная копия оказалась не нужна.

## PDF для чтения вслух (Natural Reader)
Lela слушает материалы через Natural Reader, поэтому PDF из `.md` собирается
не «чтобы красиво», а чтобы синтез речи прочёл текст РАЗБОРЧИВО. Правила ниже
выведены на слух, каждое проверялось на реальном файле.

ГЛАВНОЕ: исходный `.md` при этом НЕ ПРАВИТСЯ. Все подгонки живут в сборщике
PDF. Если в исходнике нашлась опечатка, о ней можно сказать, но лезть в файл
без отдельной просьбы нельзя — задача была про PDF.

Отсюда же правило про ЦИТАТЫ. Lela слушает PDF и цитирует куски прямо оттуда,
поэтому кривая фраза может быть следствием ОЗВУЧКИ, а не текста. Прежде чем
что-то править, понять, где источник: если проблема в том, КАК читается, чинить
надо `tools/tts_pdf.py`, а не разбор. Так я полезла править `.md` из-за того,
что карта «символ → последняя позиция» читалась как «символ значит последняя
позиция», хотя чинить надо было подсказку в сборщике.

### Что синтез речи проглатывает и что с этим делать
| В тексте | Как читается | Что делаем |
|---|---|---|
| `-` между пробелами (`a - b`) | не произносится | рядом слово «минус» |
| `-` перед цифрой (`-5`) | «минус пять», верно | не трогаем |
| `−` U+2212 | не произносится вообще | приводим к обычному дефису |
| `→` в выводе (`сигнал → класс`) | не произносится | рядом слово «значит» |
| `→` в отображении (`«ключ → значение»`, `` `a→0` ``) | не произносится | рядом слово «соответствует» |

У стрелки две роли, и подсказка зависит от роли: вывод читается «значит»,
запись отображения — «соответствует», иначе выходит «символ значит последняя
позиция». Роль определяется по обрамлению: стрелка внутри кавычек-ёлочек или
внутри инлайнового кода считается отображением. Реализация — функция
`arrow_word` в `tools/tts_pdf.py`.

Слова-подсказки красим бледно-серым (`#cdd3dd`): глазу почти не видно, а в
текстовом слое PDF они есть, и Natural Reader их произносит.

Подсказки ставятся ТОЛЬКО в прозе и текстовых блоках. В блоках с кодом
(```` ```java ````) их быть не должно — там они мешают читать сам код.
Признак: у блока с языком pandoc ставит `<code class="language-java">`,
у текстового блока класса нет.

### Паузы
Natural Reader делает паузу только на точке. Без неё читает монотонно,
сливая всё подряд. Поэтому серая точка ставится в конец:
- каждого заголовка;
- каждого пункта списка;
- каждой ячейки таблицы (иначе вся таблица читается одним предложением);
- каждой содержательной строки в ТЕКСТОВОМ блоке — примеры ввода-вывода
  и ASCII-схемы читаются построчно и тоже сливаются.

Не ставим, если строка уже кончается на `.!?:…»` и если в строке нет ни букв,
ни цифр (например строка из одних стрелок `↑ ↑`).

### Склейки слов
Пробел рядом с инлайновым `<code>` теряется при извлечении текста, и синтез
слышит «участкаk». Лечится неразрывным пробелом U+00A0. Но если он оказывается
одиноким узлом между двумя тегами (`</strong> <code>`), теряется и он —
тогда пробел переносится ВНУТРЬ предыдущего тега.
Проверка после сборки: искать в извлечённом тексте кириллицу вплотную
к латинице.

### Размеры
Основной текст 13 pt, таблицы 11.5 pt, код в блоках 10.5 pt, инлайновый код
11 pt, H1 23 pt, H2 17 pt. Мельче — Lela не читает.

### Как собирается
Готовый сборщик лежит в проекте: `tools/tts_pdf.py`. Все правила выше в нём
уже реализованы, заново выводить их не надо.

```
pip install weasyprint beautifulsoup4 --break-system-packages
python3 tools/tts_pdf.py A.md B.md -o /путь/выход.pdf
```

Запускается в Linux-песочнице Клода, не на машине Lela: нужны pandoc,
WeasyPrint и BeautifulSoup, на Windows их нет. Шрифты DejaVu, кириллица есть.
Ссылки на локальные `.md` разворачиваются в текст, внешние остаются.
Несколько файлов склеиваются в один PDF, каждый следующий с новой страницы.

### Куда класть готовый PDF
Все PDF для Natural Reader складываются в папку `PDF4 natural reader` внутри
`Загрузки` (`C:\Users\Ola\Downloads\PDF4 natural reader`), а не в папку проекта:
это расходный материал для прослушивания, в репозитории ему делать нечего.
Собирается PDF в песочнице, затем копируется туда через desktop-commander.

Собирать надо ВСЮ тему целиком, а не один файл: к разбору задачи добавляются
справочники, на которые он опирается.

Скрипт сам печатает отчёт и ПРОВЕРЯЕТ результат извлечением текста через
`pypdf`: сколько подсказок поставлено, не осталось ли U+2212, нет ли склеек
кириллицы с латиницей. На глаз это всё не видно, поэтому отчёт читать
обязательно.

## Решение сверять с ограничениями из его же .md
Тесты ловят неправильный ответ, но НЕ ловят неоптимальный: лишняя работа даёт
тот же результат, и все проверки остаются зелёными. Поэтому после того, как
решение написано и прогнано, отдельным шагом перечитать в его `.md` разделы
«Ограничения» и follow-up и спросить: не нарушает ли код собственное требование.

Так был пропущен промах в `MoveZeroes`: в ограничениях стояло «минимизировать
число операций записи», а первый проход писал `nums[writeIndex] = nums[readIndex]`
даже когда указатели идут вровень, то есть копировал элемент сам в себя. На
массиве без нулей это n холостых записей. Ошибку заметила Lela, тесты молчали.

Что проверять:
- требования вида «минимизировать число операций / записей / проходов»;
- обещанная в `.md` сложность по времени и по памяти против фактической;
- follow-up из условия задачи (например «а если Unicode», «а если массив нельзя
  менять») — либо решение его закрывает, либо в `.md` явно сказано, что нет;
- заявленное «на месте (in-place)» — нет ли скрытой копии массива или строки.

Отдельно: пользователю честно говорить, что именно проверено запуском, а что
осталось на моём суждении. Корректность подтверждена тестами, оптимальность
и идиоматичность — нет.

## Утверждение шире ограничений задачи — либо тест на него, либо сузить текст
Тесты я пишу по разделу «Ограничения». Но в тексте `.md` и в комментариях
регулярно появляются утверждения ШИРЕ этих ограничений: «обобщение на
произвольный алфавит», «работает и на Unicode», «подойдёт и для потока»,
«это follow-up задачи». Такое утверждение — обещание, и на каждое обещание
нужен свой тест. Нет теста — значит утверждение надо сузить до того, что
реально проверено, или убрать.

Проверять перед сдачей задачи: пройтись по собственному тексту и на каждую
фразу, выходящую за ограничения, спросить «а какой тест это подтверждает?».

Три случая, на которых правило и родилось (все три поймала Lela, за один день):
- `FirstUniqueChar`: метод объявлен «обобщением на произвольный алфавит», а ключ
  карты стоял `Character` — 16 бит, потолок U+FFFF. На `"🐷🐽"` он бы сломался:
  у пятачка и свиного рыла ОБЩАЯ старшая половина суррогатной пары U+D83D, карта
  сочла бы символ повторяющимся и вернула бы 1 (половинку пары) вместо 0. Тест
  на эмодзи упал бы сразу — но его не было, потому что в ограничениях задачи
  стоит «только строчные латинские буквы».
- `ReverseString`: раздел про Unicode назван follow-up'ом задачи, хотя на
  LeetCode у 344 раздела Follow up нет вовсе.
- `ReverseString`, продолжение: когда это вскрылось, я переименовала раздел
  вместо того чтобы удалить ненужный код. Ярлык переклеен — обещание осталось.

Общее у всех трёх: заявление шире, чем то, что реально проверено запуском.

## После правки файла — перечитать его ЦЕЛИКОМ
Отредактировал файл (.md, .java, .html) — сразу перечитай его от начала до конца
и проверь на несостыковки. Файлы в проекте небольшие, это стоит копейки, а правки
накапливаются и ломают текст незаметно.

Так уже ломался `Pattern_TwoPointers.md`: подвидов объявлено два, а формы стояли
на том же уровне заголовка и читались как третий подвид; определение формы
«быстрый/медленный» противоречило собственному примеру; «Частая путаница»
отрицала то, что двумя разделами выше стало частью приёма; эвристика требовала
сортировки, хотя абзацем выше сказано, что сортировка отсекает лишь один подвид.
Каждая правка по отдельности была верной — сломалось согласование.

Что проверять при перечитывании:
- заголовки и вложенность: обещано «два подвида» — значит на этом уровне ровно
  два заголовка, вложенное уходит уровнем ниже;
- числительные в тексте против фактического количества пунктов ниже;
- определение против своих же примеров (пример не должен опровергать определение);
- обобщения: утверждение в разделе «в чём суть» должно быть верно для ВСЕХ
  подвидов и форм, иначе его место — в разделе про конкретный подвид;
- ссылки на разделы и файлы: раздел с таким названием существует, файл существует;
- разделы «частые ловушки» и «см. также»: не противоречат ли новой структуре;
- в .java — комментарий и Javadoc против фактического кода после правки.

## Чем Клод читает и правит файлы проекта
Папка проекта примонтирована в Cowork, поэтому читать и править файлы внутри неё
нужно ТОЛЬКО штатными инструментами Cowork (Read / Write / Edit / Grep).
Через desktop-commander файлы проекта не читать — ни `read_file`, ни косвенно
скриптом в терминале, который сам открывает файл. Если проверке нужны вычисления
по содержимому (посчитать колонки в ASCII-схеме, сверить куски текста), сначала
прочитать файл штатно, а затем передать уже прочитанный текст в скрипт.

desktop-commander остаётся для двух вещей:
- действия на машине: компиляция, запуск тестов, git, просмотр каталогов;
- чтение того, что ВНЕ примонтированной папки — например `src.zip` из JDK
  (`C:\Users\Ola\.jdks\jbr-25.0.3\lib\src.zip`), другие проекты, Downloads.

Из desktop-commander разрешены только терминал (`start_process`,
`interact_with_process`, `read_process_output`) и чтение (`read_file`).
`edit_block`, `write_file`, `move_file`, `start_search` и прочее — не использовать.

## Сборка Клодом для самопроверки — ЛОКАЛЬНО, не в песочнице
Компилировать и прогонять тесты нужно на машине пользователя, через терминал
desktop-commander (`start_process`, оболочка PowerShell). Там уже стоит JDK 25
(JetBrains Runtime), `javac` и `java` доступны в PATH — то есть та же самая JDK,
которой собирает IntelliJ IDEA. Отдельный тарбол и распаковка не нужны.

Рабочая последовательность (пример для блока 2):
```
cd C:\Users\Ola\IdeaProjects\interview\algo-roadmap
javac -encoding UTF-8 -d out\claudecheck src\block02_strings_stack\*.java
[Console]::OutputEncoding=[System.Text.Encoding]::UTF8
java "-Dfile.encoding=UTF-8" "-Dstdout.encoding=UTF-8" -cp out\claudecheck block02_strings_stack.ValidParentheses
```
Каталог `out\` уже в .gitignore, поэтому `out\claudecheck` можно смело удалять
после прогона.

Две грабли PowerShell, обе проверены на практике:
- флаги вида `-Dfile.encoding=UTF-8` ОБЯЗАТЕЛЬНО брать в кавычки, иначе PowerShell
  разрезает строку и получается `Could not find or load main class .encoding=UTF-8`;
- без `[Console]::OutputEncoding=...UTF8` русские сообщения тестов выводятся
  кракозябрами.

Про Linux-песочницу: она остаётся полезной для вспомогательных проверок, не
требующих Java, — например, прогнать логику визуализации через Node и сверить её
с Java-решением. Но JDK там нет (системный java — JRE 11 без javac), тарбол из
проекта убран, так что Java-код в песочнице НЕ собираем.
