# String — строка

*Класс `java.lang.String`*

Справочник в объёме собеседования. Проверено на JDK 25 (JetBrains Runtime).

## Что это

`String` — неизменяемый (immutable) объект, хранящий последовательность символов. Объявлен как `public final class String`, то есть унаследоваться от него нельзя.

Внутри лежит **массив байтов**, а не символов:

```java
private final byte[] value;
private final byte coder;      // 0 = LATIN1, 1 = UTF16
```

Так с Java 9 — это оптимизация под названием compact strings. Если все символы строки помещаются в один байт (латиница, цифры, знаки препинания), строка хранится по байту на символ. Как только появляется что-то за пределами Latin-1 — кириллица, эмодзи — включается режим UTF-16 и на символ уходит два байта.

Проверено:

```
"abc": coder=0 (LATIN1)  byte[].length=3   length()=3
"кот": coder=1 (UTF16)   byte[].length=6   length()=3
"🐷" : coder=1 (UTF16)   byte[].length=4   length()=2
```

Русский текст занимает вдвое больше памяти, чем такой же по длине английский, — прямое следствие этой схемы.

### Режим выбирается на всю строку, а не посимвольно

Это не мелочь, а практическое следствие с неприятным масштабом. `coder` — одно поле на весь объект, поэтому **один символ вне Latin-1 переводит в UTF-16 всю строку целиком**, включая тысячу соседних латинских букв, каждой из которых теперь нужно по два байта вместо одного.

Проверено:

```
"a" × 1000            coder=0 (LATIN1)  byte[].length=1000
"a" × 1000 + "🐷"     coder=1 (UTF16)   byte[].length=2004
```

Свинья добавила не 4 байта, а **1004**: свои четыре плюс удвоение всей остальной строки. Строка потяжелела вдвое из-за одного символа.

Где это стреляет: логи, пользовательский ввод, тексты сообщений. Одна эмодзи в подписи или один тире-длинное вместо дефиса — и объект в памяти вдвое толще. На единичной строке неважно, на миллионе строк в кеше уже заметно.

Отсюда же понятно, почему compact strings дали такой эффект при выходе в Java 9: до этого **все** строки хранились как UTF-16, то есть английский текст всегда занимал вдвое больше необходимого.

### Почему второй режим — UTF-16, а не UTF-8

Логичный вопрос: раз уж в Java 9 всё равно переделывали хранилище, почему вторым режимом взяли UTF-16, а не UTF-8, которая компактнее и победила везде снаружи?

Причина в контракте `charAt(int)`. Он обязан работать за **`O(1)`** — на этом стоят все циклы обхода строк, вся регулярка, весь парсинг. Обращение по индексу должно быть арифметикой над адресом, а не поиском.

Чтобы разобраться, надо развести три разные вещи, которые легко слипаются:

| Уровень | Что это | Где живёт |
|---------|---------|-----------|
| символ (кодовая точка) | то, что видит человек: `a`, `б`, 🐷 | понятие Unicode, в коде — `int` |
| `char` (кодовая единица UTF-16) | то, чем оперирует API `String` и что нумерует `charAt` | тип языка, 16 бит |
| байт | то, что реально лежит в массиве `value` | `private final byte[] value` |

Элемент массива `value` — всегда байт, тут вариантов нет. Вопрос в другом: **сколько байтов занимает один `char`** в выбранном режиме хранения. Именно от этого зависит, можно ли вычислить адрес i-го `char` формулой.

| Режим хранения | Байт на один `char` | Где лежит i-й `char` | `charAt(i)` |
|----------------|---------------------|----------------------|-------------|
| LATIN1 | всегда 1 | `value[i]` | `O(1)` |
| UTF-16 | всегда 2 | `value[2i]` и `value[2i+1]` | `O(1)` |
| UTF-8 | от 1 до 3 (для BMP) | формулой не вычислить | `O(n)` |

В первых двух случаях позиция считается умножением — это и есть «фиксированная ширина». В UTF-8 длина символа закодирована в его собственных старших битах, разные символы занимают разное число байтов, и узнать, где начинается i-й, можно только просканировав строку с начала. `charAt` стал бы линейным, а обычный цикл `for (int i = 0; i < s.length(); i++)` — квадратичным. Это сломало бы производительность всего существующего кода, не поменяв в нём ни строчки.

Отдельно стоит отметить, чтобы не путаться: **UTF-16 тоже переменной длины**, символ вне базовой плоскости занимает в ней два `char`. Но переменная длина у неё на уровне *символов*, а не на уровне `char`: один `char` — всегда ровно два байта. `charAt` нумерует именно `char`, поэтому ему этого достаточно. Плата за такой компромисс — что один `char` не всегда равен одному символу, о чём весь следующий раздел.

LATIN1 выбрали по той же причине: один байт на единицу, фиксированно. Он даёт компактность UTF-8 на латинице, ничего не ломая. А там, где LATIN1 не хватает, переключаться можно только на кодировку с фиксированной единицей — то есть на UTF-16.

## char — не символ

Главное, что нужно понять про строки в Java, и главный источник ошибок.

**`char` — это кодовая единица UTF-16**, 16-битное беззнаковое целое. Не символ. Совпадение с символом верно только для базовой многоязычной плоскости (BMP) — кодов до `U+FFFF`, куда входят латиница, кириллица, иероглифы CJK.

Символы выше `U+FFFF` — эмодзи, редкие иероглифы, древние письменности — в 16 бит не влезают и кодируются **суррогатной парой**: двумя значениями `char` из специально зарезервированных диапазонов.

```
старшая половина (high surrogate):  D800…DBFF
младшая половина (low surrogate):   DC00…DFFF
```

Эти диапазоны навсегда пустые: настоящих символов там нет и не будет. Поэтому половинку нельзя спутать с буквой — встретив `U+D83D`, точно знаешь, что это часть пары.

Пересчёт кодовой точки в пару:

```
0x1F437 − 0x10000 = 0xF437
старшая: 0xD800 + (0xF437 >> 10)    = 0xD83D
младшая: 0xDC00 + (0xF437 & 0x3FF)  = 0xDC37
```

### Откуда это взялось

Наследство 1995 года. При проектировании Java Unicode обещал уместиться в 16 бит, и `char` сделали 16-битным. В 2001-м Unicode вышел за эту границу, но менять `char` было поздно — сломался бы весь существующий код. В Java 5 сверху накрутили UTF-16 с суррогатными парами.

Java тут не одинока: ровно то же наследство в JavaScript, C# и Windows API.

## length() против codePointCount()

`length()` документирован честно: он возвращает **количество значений `char`**, а не символов. Двадцать лет эти числа совпадали, поэтому все привыкли читать его как «длина».

```
строка: a🐷b🐽c
length()       = 7
codePointCount = 5
```

Пять символов, семь `char`: каждая свинья занимает два.

| Что нужно | Метод |
|-----------|-------|
| количество `char` (размер хранилища) | `length()` |
| количество символов | `codePointCount(0, length())` |
| символ по позиции в `char` | `charAt(i)` — вернёт половину пары |
| кодовая точка по позиции в `char` | `codePointAt(i)` |
| перебрать символы | `codePoints()` |

## Резать строку по индексам char небезопасно

`substring` работает в индексах `char`, поэтому легко разрубить символ пополам:

```
"🐽".substring(0, 1)  →  U+D83D, одинокий суррогат
```

Отрисовать его нечем, консоль показывает `?`. Склеишь половинки обратно — символ снова целый, но в промежутке в строке лежит мусор.

### offsetByCodePoints — как резать правильно

```java
public int offsetByCodePoints(int index, int codePointOffset)
```

Метод отвечает на вопрос: **если отступить от позиции `index` на `codePointOffset` символов, на каком индексе `char` мы окажемся?** То есть он переводит «номер символа» в «индекс `char`», перешагивая суррогатные пары целиком.

Для строки `a🐷b🐽c` — пять символов, семь `char`:

```
 символы:   a      🐷        b      🐽       c
 char:     [0]   [1][2]     [3]   [4][5]    [6]
```

| `N` | `offsetByCodePoints(0, N)` | символ |
|-----|---------------------------|--------|
| 0 | 0 | `a` |
| 1 | 1 | 🐷 |
| 2 | 3 | `b` — перескочили пару целиком |
| 3 | 4 | 🐽 |
| 4 | 6 | `c` |

Видно главное: индекс `char` растёт неравномерно, скачками по 1 или по 2, потому что суррогатная пара занимает две позиции. Именно это и мешает адресовать символы напрямую.

Отсюда безопасная нарезка: индексы берём не «на глаз», а через этот метод.

```java
int start = text.offsetByCodePoints(0, 1);   // начало 1-го символа
int end   = text.offsetByCodePoints(0, 2);   // начало 2-го = конец 1-го
text.substring(start, end);                  // → 🐷

text.substring(1, 2);                        // → половина пары
```

Оба вызова проверены запуском и дают именно то, что написано.

Замечание про стоимость: метод не индексирует строку заранее, а идёт по ней от `index`, поэтому один вызов — `O(codePointOffset)`. Для прохода по всем символам в цикле он даст квадрат; там правильнее `codePoints()` или ручной шаг с `Character.charCount(codePoint)`.

Рабочий пример со всеми тремя способами перебора и сравнением правильной нарезки с наивной — класс `block02_strings_stack.CodePointOffsets`, запускается через `main()`.

### Character.toChars — из кодовой точки обратно в char

Преобразование в обратную сторону: `codePointAt` даёт кодовую точку как `int`, а `String` и `StringBuilder` принимают `char`. Мост между ними — `Character.toChars(int codePoint)`: возвращает `char[]` из одной или двух единиц UTF-16.

```
U+61     -> char[1] = U+0061           charCount=1  → "a"
U+431    -> char[1] = U+0431           charCount=1  → "б"
U+1F437  -> char[2] = U+D83D U+DC37    charCount=2  → "🐷"
```

Если нужна только длина будущего массива, без него самого, есть `Character.charCount(codePoint)` — он и используется как шаг при ручном обходе строки.

Приведением тут не обойтись: `(char)` просто обрубит старшие биты и вернёт мусор.

```java
new String(Character.toChars(0x1F437))   // → 🐷
(char) 0x1F437                           // → 62519, свинья потеряна
```

У `StringBuilder` для этого есть отдельный метод, он делает то же самое без промежуточного массива:

```java
builder.appendCodePoint(codePoint);
```

Сводка того, чем переводить между уровнями:

| Из чего | Во что | Чем |
|---------|--------|-----|
| индекс `char` | кодовая точка | `codePointAt(i)` |
| кодовая точка | массив `char` | `Character.toChars(cp)` |
| кодовая точка | длина в `char` | `Character.charCount(cp)` |
| кодовая точка | дописать в буфер | `builder.appendCodePoint(cp)` |
| номер символа | индекс `char` | `offsetByCodePoints(0, n)` |

## Неизменяемость и её следствия

Любая операция над строкой возвращает **новый объект**, исходный не меняется. Отсюда два практических правила.

**Конкатенация в цикле — это `O(n²)`.** Каждое `+=` копирует всё накопленное в новый массив. В цикле используется `StringBuilder`, у него добавление амортизированное `O(1)`.

```java
// плохо: на каждой итерации копируется вся строка
String result = "";
for (String part : parts) {
    result += part;
}

// правильно
StringBuilder builder = new StringBuilder();
for (String part : parts) {
    builder.append(part);
}
String result = builder.toString();
```

Вне цикла `+` безопасен: компилятор сам разворачивает его в эффективную конкатенацию.

**`toCharArray()` создаёт копию** — `O(n)` времени и памяти. Часто удобно, но если задача требует `O(1)` дополнительной памяти, придётся работать через `charAt`.

Зато неизменяемость даёт и выгоды: строку можно безопасно шарить между потоками, использовать как ключ `HashMap` (хеш кешируется и не протухает), и она не может измениться у вас за спиной после проверки.

## Сравнение: equals, а не ==

`==` сравнивает **ссылки**, `equals` — содержимое. Классическая ловушка:

```
"ab" == "ab"                                       → true
"ab" == new StringBuilder("a").append("b").toString() → false
```

Первое даёт `true` не потому, что `==` работает со строками, а из-за **пула строк**: одинаковые литералы компилятор складывает в общий пул и они оказываются одним объектом. Строка, собранная в рантайме, в пул не попадает — и сравнение ломается ровно тогда, когда данные приходят извне, а не написаны в коде.

Для игнорирования регистра — `equalsIgnoreCase`. Для сортировки — `compareTo`.

## Сложность операций

| Операция | Сложность |
|----------|-----------|
| `length()` | `O(1)` |
| `charAt(i)` | `O(1)` |
| `equals` | `O(n)` |
| `hashCode()` | `O(n)` при первом вызове, дальше `O(1)` — кешируется |
| `substring` | `O(n)` — копирует |
| `indexOf` | `O(n·m)` в худшем случае |
| `concat` / `+` | `O(n + m)` — создаёт новый объект |
| `codePointCount` | `O(n)` |
| `offsetByCodePoints` | `O(offset)` |

## Типичные вопросы на собеседовании

**Почему `String` неизменяемый?**
Безопасность потоков, кеширование хеша, надёжность в роли ключа `HashMap`, работа пула строк. Плюс защита от подмены значения после проверки.

**Что вернёт `"🐷".length()`?**
Два. `length()` считает значения `char`, а эмодзи занимает суррогатную пару. Символов при этом один — это покажет `codePointCount`.

**Почему нельзя сравнивать строки через `==`?**
Он сравнивает ссылки. Для литералов часто «случайно работает» из-за пула строк, но для строк, собранных в рантайме, даёт `false`.

**Чем `String` отличается от `StringBuilder`?**
`String` неизменяем, каждая операция создаёт новый объект. `StringBuilder` изменяемый и не синхронизирован. Есть ещё `StringBuffer` — то же самое, но синхронизированный; сегодня почти не нужен.

**Почему конкатенация в цикле плохо?**
`O(n²)`: каждая итерация копирует всё накопленное. Нужен `StringBuilder`.

**Как правильно перебрать символы строки?**
`codePoints()`, если во входе возможно что-то вне базовой плоскости. `charAt` в цикле — только когда алфавит заведомо ограничен, как в задачах с латиницей.
