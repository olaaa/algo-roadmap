# 242. Valid Anagram
*Проверка анаграммы (дословно: корректная анаграмма)*

**Сложность:** Easy · **Паттерн:** счётчик частот · **Класс:** `block02_strings_stack.ValidAnagram`

## Условие

Даны две строки `s` и `t`. Нужно определить, является ли `t` анаграммой строки `s`.

Анаграмма — строка, составленная из **тех же символов в том же количестве**, но, как правило, в другом порядке. То есть `t` анаграмма `s`, если каждая буква встречается в обеих строках одинаковое число раз.

Строка считается анаграммой самой себя: порядок менять не обязательно.

## Примеры

### Пример 1

```
Вход:  s = "anagram", t = "nagaram"
Выход: true
```

Обе строки содержат `a` три раза, `n` — два, `g`, `r`, `m` — по одному.

### Пример 2

```
Вход:  s = "rat", t = "car"
Выход: false
```

Длины совпадают, но набор букв разный: `t` вместо `c`.

### Пример 3

```
Вход:  s = "aacc", t = "ccac"
Выход: false
```

Тонкий случай: **набор букв одинаковый**, а количества разные — в первой строке две `a` и две `c`, во второй одна `a` и три `c`. Проверять достаточно только присутствия буквы нельзя, нужно именно количество.

### Пример 4

```
Вход:  s = "ab", t = "abc"
Выход: false
```

Разная длина — дальше можно не смотреть.

## Ограничения

- `1 <= s.length, t.length <= 5 * 10^4`
- `s` и `t` состоят только из строчных латинских букв

## Почему такие ограничения

Алфавит из 26 строчных букв — ключевое упрощение. Оно позволяет заменить хеш-таблицу обычным массивом `int[26]`, где индекс буквы вычисляется как `symbol - 'a'`. Массив быстрее хеш-таблицы и не требует упаковки в `Integer`, а память от длины строки не зависит вовсе — всегда 26 ячеек. Именно поэтому в разделе про сложность стоит `O(1)` по памяти, хотя счётчик как будто «хранит данные».

Длина до `5 * 10^4` отсекает сравнение «в лоб» — для каждой буквы первой строки искать пару во второй за `O(n²)`.

## Идея решения

Порядок символов не важен, важны только количества. Значит задача сводится к сравнению двух наборов частот.

**Первая проверка — длины.** Если строки разной длины, анаграммой они быть не могут. Это дешёвая отсечка за `O(1)`, и она же избавляет от целого класса ошибок дальше.

**Дальше — один массив на 26 счётчиков вместо двух.** Наивно было бы посчитать частоты отдельно для `s`, отдельно для `t` и сравнить два массива. Но можно обойтись одним: идём по обеим строкам одновременно, для буквы из `s` счётчик увеличиваем, для буквы из `t` — уменьшаем.

Если строки анаграммы, каждое увеличение рано или поздно компенсируется уменьшением, и в конце **весь массив обнулится**. Любая ненулевая ячейка означает перекос: положительная — буква лишняя в `s`, отрицательная — лишняя в `t`.

Единый проход возможен именно потому, что длины уже проверены и совпадают.

### Почему в конце проверяем нули, а не возвращаем true

Это тот же приём, что и в [`ValidParentheses`](ValidParentheses.md): внутри цикла нарушений не видно в принципе, потому что цикл только копит счётчики и ничего не сравнивает. Ответ целиком определяется остатком — состоянием массива после прохода. Разбор приёма — пункт 4 в [`heuristics.md`](../../heuristics.md).

### Альтернатива: сортировка

Отсортировать обе строки и сравнить посимвольно. Решение в две строки, его стоит назвать на собеседовании как первое пришедшее в голову:

```java
char[] sortedFirst = s.toCharArray();
char[] sortedSecond = t.toCharArray();
Arrays.sort(sortedFirst);
Arrays.sort(sortedSecond);
return Arrays.equals(sortedFirst, sortedSecond);
```

Оно короче и не зависит от алфавита, но медленнее: `O(n log n)` против `O(n)`, плюс `O(n)` памяти на копии массивов. Хороший ход — предложить его, сразу назвать сложность и тут же дать линейный вариант.

### Follow-up: а если Unicode?

Стандартный дополнительный вопрос интервьюера. Массив на 26 ячеек рассыпается, как только появляются символы вне латиницы. Замена — `HashMap` со счётчиками, но есть подвох: тип ключа должен быть **кодовая точка** (`int`), а не `char`.

Символ вне базовой плоскости (эмодзи, редкие иероглифы) занимает в Java два `char` — суррогатную пару. Если считать по `char`, такой символ развалится на две половинки, и строки с разными эмодзи могут ошибочно совпасть по счётчикам. Поэтому в варианте для Unicode идём по `codePoints()`, а не по `charAt`.

Заодно там не нужна отдельная проверка длин: разница в количестве символов сама даст ненулевой счётчик.

## Сложность

| Решение | Время | Память |
|---------|-------|--------|
| Массив частот (эталон) | `O(n)` | `O(1)` — всегда 26 ячеек |
| Сортировка | `O(n log n)` | `O(n)` |
| `HashMap` по кодовым точкам | `O(n)` | `O(k)`, где `k` — число различных символов |
