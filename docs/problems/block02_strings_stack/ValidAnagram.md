# 242. Valid Anagram
*Проверка анаграммы (дословно: корректная анаграмма)*

**Сложность:** Easy · **Паттерн:** счётчик частот · **Класс:** `block02_strings_stack.ValidAnagram`

## Условие

Даны две строки `s` и `t`. Нужно определить, является ли `t` анаграммой строки `s`.

Анаграмма — строка, составленная из **тех же символов в том же количестве**, но, как правило, в другом порядке. То есть `t` анаграмма `s`, если каждая буква встречается в обеих строках одинаковое число раз.

Строка считается анаграммой самой себя: порядок менять не обязательно.

## Примеры

### Пример 1

```
Вход:  s = "anagram", t = "nagaram"
Выход: true
```

Обе строки содержат `a` три раза, `n` — два, `g`, `r`, `m` — по одному.

### Пример 2

```
Вход:  s = "rat", t = "car"
Выход: false
```

Длины совпадают, но набор букв разный: `t` вместо `c`.

### Пример 3

```
Вход:  s = "aacc", t = "ccac"
Выход: false
```

Тонкий случай: **набор букв одинаковый**, а количества разные — в первой строке две `a` и две `c`, во второй одна `a` и три `c`. Проверять достаточно только присутствия буквы нельзя, нужно именно количество.

### Пример 4

```
Вход:  s = "ab", t = "abc"
Выход: false
```

Разная длина — дальше можно не смотреть.

## Ограничения

- `1 <= s.length, t.length <= 5 * 10^4`
- `s` и `t` состоят только из строчных латинских букв

## Почему такие ограничения

Алфавит из 26 строчных букв — ключевое упрощение. Оно позволяет заменить хеш-таблицу обычным массивом `int[26]`, где индекс буквы вычисляется как `symbol - 'a'`. Массив быстрее хеш-таблицы и не требует упаковки в `Integer`, а память от длины строки не зависит вовсе — всегда 26 ячеек. Именно поэтому в разделе про сложность стоит `O(1)` по памяти, хотя счётчик как будто «хранит данные».

### Почему работает `symbol - 'a'`

В общем виде формула такая: **индекс = код символа − код первой буквы алфавита**. Для строчной латиницы первая буква `'a'`, отсюда и запись.

Держится она на двух свойствах Java и одном свойстве таблицы символов:

**`char` — числовой тип.** Это 16-битное беззнаковое целое, хранящее код символа, а не отдельная «буквенная» сущность. В арифметике он повышается до `int`, поэтому выражение `symbol - 'a'` имеет тип **`int`** — приведение для индексации массива не нужно.

**Буквы `a`–`z` идут в таблице подряд**, коды 97…122. Проверено запуском:

```
'a' = 97,  'z' = 122
'a' - 'a' = 0
'c' - 'a' = 2
'z' - 'a' = 25
```

Вычитание 97 сдвигает диапазон в 0…25 — ровно индексы массива из 26 ячеек. Непрерывность здесь принципиальна: будь в алфавите разрывы, часть индексов уходила бы в пустоту или за границу.

**Регистр обязан быть одним.** По ограничениям задачи на входе только строчные, поэтому проверка не нужна. Но если бы верхний регистр допускался, формула сломалась бы молча: `'C' - 'a' = -30`, то есть `ArrayIndexOutOfBoundsException`. Страховка — нормализовать регистр до вычитания: `Character.toLowerCase(symbol) - 'a'`.

Длина до `5 * 10^4` отсекает сравнение «в лоб» — для каждой буквы первой строки искать пару во второй за `O(n²)`.

## Идея решения

Порядок символов не важен, важны только количества. Значит задача сводится к сравнению двух наборов частот.

**Первая проверка — длины.** Если строки разной длины, анаграммой они быть не могут. Это дешёвая отсечка за `O(1)`, и она же избавляет от целого класса ошибок дальше.

**Дальше — один массив на 26 счётчиков вместо двух.** Наивно было бы посчитать частоты отдельно для `s`, отдельно для `t` и сравнить два массива. Но можно обойтись одним: идём по обеим строкам одновременно, для буквы из `s` счётчик увеличиваем, для буквы из `t` — уменьшаем.

Если строки анаграммы, каждое увеличение рано или поздно компенсируется уменьшением, и в конце **весь массив обнулится**. Любая ненулевая ячейка означает перекос: положительная — буква лишняя в `s`, отрицательная — лишняя в `t`.

Единый проход возможен именно потому, что длины уже проверены и совпадают.

### Что делает каждая переменная

| Переменная | Что хранит | Зачем она нужна |
|---|---|---|
| `s`, `t` | две входные строки | только читаются; какая из них «первая», решает лишь знак в счётчике |
| `LOWERCASE_LETTER_COUNT` | константу 26 | размер алфавита из условия. Именованная константа вместо числа в коде: из `new int[26]` не видно, почему именно 26 |
| `letterCounts` | массив из 26 счётчиков, по одному на букву | состояние алгоритма. Один массив вместо двух: буква из `s` его увеличивает, буква из `t` уменьшает, и анаграмма опознаётся по тому, что всё обнулилось |
| `currentIndex` | позицию в ОБЕИХ строках сразу | одним индексом читаются оба входа, потому что длины уже проверены и совпадают. Без этой проверки индекс вышел бы за границу более короткой строки |
| `count` | значение очередной ячейки во втором цикле | переменная цикла `for-each` по массиву счётчиков; проверяется на ноль |

В двух других методах класса состояние другое. У сортировки это `sortedFirst` и `sortedSecond` — именно копии строк, а не сами строки: `String` в Java неизменяема, отсортировать её на месте нельзя (разбор ниже). У юникодного варианта — `codePointCounts`, карта «кодовая точка → счётчик»: массив под миллион с лишним кодовых точек заводить бессмысленно, а `char` ключом быть не может, потому что эмодзи занимает два `char`.

### Почему в конце проверяем нули, а не возвращаем true

Это тот же приём, что и в [`ValidParentheses`](ValidParentheses.md): внутри цикла нарушений не видно в принципе, потому что цикл только копит счётчики и ничего не сравнивает. Ответ целиком определяется остатком — состоянием массива после прохода. Разбор приёма — пункт 4 в [`heuristics.md`](../../heuristics.md).

### Альтернатива: сортировка

Отсортировать обе строки и сравнить посимвольно. Решение в две строки, его стоит назвать на собеседовании как первое пришедшее в голову:

```java
char[] sortedFirst = s.toCharArray();
char[] sortedSecond = t.toCharArray();
Arrays.sort(sortedFirst);
Arrays.sort(sortedSecond);
return Arrays.equals(sortedFirst, sortedSecond);
```

Оно короче и не зависит от алфавита, но медленнее: `O(n log n)` против `O(n)`, плюс `O(n)` памяти на копии массивов. Хороший ход — предложить его, сразу назвать сложность и тут же дать линейный вариант.

### Follow-up: а если Unicode?

Стандартный дополнительный вопрос интервьюера. Массив на 26 ячеек рассыпается, как только появляются символы вне латиницы.

#### Почему нельзя просто взять другую первую букву

Первая мысль — оставить тот же приём, поменяв алфавит: для русского писать `symbol - 'а'` и завести массив на 33 ячейки. Не сработает, и вот почему. Проверено запуском:

```
'а' = 1072,  'я' = 1103,  'ё' = 1105
'я' - 'а' = 31
'ё' - 'а' = 33
```

Буквы `а`–`я` действительно идут подряд, но это **32** буквы, а `ё` в таблице вынесена отдельно и стоит уже **за** `я`. То есть непрерывного диапазона из 33 букв, на котором держался весь приём, у русского алфавита просто нет: `ё` пришлось бы обрабатывать отдельной веткой.

Для произвольного Unicode всё ещё хуже — алфавит заранее неизвестен, и размер массива взять неоткуда.

#### Что использовать вместо массива

Замена — `HashMap` со счётчиками, но есть подвох: тип ключа должен быть **кодовая точка** (`int`), а не `char`.

Причина в том, что `char` в Java — не символ, а кодовая единица UTF-16, и всё, что не помещается в 16 бит (эмодзи, редкие иероглифы), занимает два `char` — суррогатную пару. Подсчёт по `char` разложил бы такой символ на две половинки и считал бы не то. Поэтому в варианте для Unicode идём по `codePoints()`, а не по `charAt`.

Устройство `char`, суррогатных пар и разница `length()` против `codePointCount()` разобраны отдельно: [`docs/datastructures/String.md`](../../datastructures/String.md).

Заодно там не нужна отдельная проверка длин: разница в количестве символов сама даст ненулевой счётчик.

## Свойства решений

| Характеристика | Массив частот (эталон) | Сортировка | `HashMap` по кодовым точкам |
|---|---|---|---|
| Время | `O(n)` | `O(n log n)` | `O(n)` в среднем |
| Память | `O(1)` — всегда 26 ячеек | `O(n)` — две копии строк массивами | `O(k)`, где `k` — число различных символов |
| Проходов по входу | два: счёт по строкам, затем проверка счётчиков | по проходу на сортировку каждой строки плюс сравнение | два, как у эталона |
| Ранний выход | есть: разная длина строк отсеивается до цикла, дальше `return false` на первом ненулевом счётчике | только по длине: сортировку всё равно надо доделать целиком | только на ненулевом счётчике: проверки длин здесь нет, она не нужна — разное число символов само даст ненулевой счётчик |
| Изменяет ли вход | нет | нет: `toCharArray` отдаёт копию, исходные строки не меняются | нет |
| Требования к входу | только строчные латинские буквы — иначе индекс уйдёт за границу массива | любые символы | любые символы, включая эмодзи: ключ — кодовая точка, а не `char` |
| Детерминированность | да | да | да |
| Устойчивость к деградации | худшего случая нет, массив адресуется напрямую | худшего случая нет | `O(1)` у хеш-таблицы — амортизированная оценка, при массовых коллизиях деградирует |
| Ответ после цикла | не голое `true`, а «все счётчики обнулились» — [приём 4 из шпаргалки](../../heuristics.md) | сравнение двух отсортированных массивов | как у эталона |

Проверка длин в начале — не оптимизация, а необходимость для эталона: строки разной длины дадут ненулевую сумму счётчиков, но полагаться на это незачем, когда сравнение длин стоит `O(1)`.
