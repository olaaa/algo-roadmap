# 704. Binary Search

*Бинарный поиск (дословно: двоичный поиск)*

**Сложность:** Easy · **Паттерн:** бинарный поиск по отсортированному массиву · **Класс:** `block05_binary_search.BinarySearch`

## Условие

Дан массив целых чисел `nums`, отсортированный **по возрастанию**, и число `target`. Вернуть индекс, по которому `target` лежит в массиве, или `-1`, если такого числа в массиве нет.

Все элементы массива различны.

Требуется решение за `O(log n)`.

## Примеры

### Пример 1

```
Вход:  nums = [-1, 0, 3, 5, 9, 12], target = 9
Выход: 4
```

Девятка стоит на позиции 4 (нумерация с нуля).

### Пример 2

```
Вход:  nums = [-1, 0, 3, 5, 9, 12], target = 2
Выход: -1
```

Двойки в массиве нет. Она попадает в промежуток между `0` и `3` — то есть между соседними элементами, но не совпадает ни с одним.

### Пример 3

```
Вход:  nums = [5], target = 5
Выход: 0
```

Массив из одного элемента. Этот случай стоит держать в голове: на нём ломается вариант с условием `lowIndex < highIndex`, см. раздел про строгость условия.

### Пример 4

```
Вход:  nums = [2, 4, 6, 8], target = 9
Выход: -1
```

Число больше всех элементов массива. Левая граница доедет до правого края, границы разойдутся, метод вернёт `-1`.

## Ограничения

- `1 <= nums.length <= 10^4`
- `-10^4 < nums[i], target < 10^4`
- Все значения в `nums` **различны**
- `nums` отсортирован по возрастанию

## Почему такие ограничения

Требование `O(log n)` в условии стоит прямо, а не подразумевается: линейный проход по массиву дал бы правильный ответ и уложился бы в `10^4` элементов по времени. То есть отсечь наивное решение размером входа здесь не получается — его отсекает сама формулировка задачи.

Гарантия «все значения различны» снимает вопрос, какой из одинаковых индексов возвращать. Поиск первого или последнего вхождения — отдельная задача, и решается она другой разновидностью бинарного поиска; в этом классе её нет.

Отсортированность — то, на чём весь алгоритм держится. Это **предусловие**: метод его не проверяет, а полагается на него, см. раздел ниже.

## Идея решения

Сравниваем `target` со средним элементом ещё не исключённого участка.

- Совпало — ответ найден.
- Средний элемент **меньше** искомого. Массив отсортирован, значит и всё, что левее среднего, тоже меньше искомого. Вся левая половина вместе с самим средним элементом исключается.
- Средний элемент **больше** искомого — зеркально, исключается правая половина вместе со средним.

Каждое сравнение выбрасывает половину оставшегося. Участок из `n` элементов сжимается до пустого примерно за `log₂ n` шагов.

```java
int lowIndex = 0;
int highIndex = nums.length - 1;

while (lowIndex <= highIndex) {
    int middleIndex = (lowIndex + highIndex) / 2;
    int middleValue = nums[middleIndex];

    if (middleValue == target) {
        return middleIndex;
    }
    if (middleValue < target) {
        lowIndex = middleIndex + 1;
    } else {
        highIndex = middleIndex - 1;
    }
}
return -1;
```

Инвариант, вокруг которого построено решение: **если `target` вообще есть в массиве, он лежит на отрезке `[lowIndex .. highIndex]`**. Каждая итерация сужает отрезок, не нарушая это утверждение. Когда отрезок становится пустым, из инварианта следует, что искомого нет вовсе, — это и есть возврат `-1`.

### Что делает каждая переменная

| Переменная | Что хранит | Зачем она нужна |
|---|---|---|
| `nums` | вход, отсортированный массив | читается, не меняется |
| `target` | вход, искомое значение | второй операнд каждого сравнения |
| `lowIndex` | индекс левой границы участка поиска, включительно | всё, что левее, уже исключено сравнениями; сдвигается вправо, когда середина оказалась мала |
| `highIndex` | индекс правой границы участка поиска, включительно | всё, что правее, уже исключено; сдвигается влево, когда середина оказалась велика |
| `middleIndex` | индекс середины текущего участка | единственная позиция, которую итерация проверяет; она же становится ответом при совпадении |
| `middleValue` | значение `nums[middleIndex]` | участвует в двух сравнениях подряд — на равенство и на «меньше»; отдельная переменная избавляет от повторного чтения массива и делает сравнения читаемыми |

Обе границы **включительные**: позиция, на которую они указывают, ещё не проверена. Из этого следуют и нестрогое условие цикла, и единицы в сдвигах — оба разбора ниже.

Имена `lowIndex` и `highIndex` — та же пара, что в литературе зовётся `low` / `high` (у Макдауэлл именно так, см. раздел «Опора в книге»). Существительное `Index` добавлено, потому что `low` само по себе — прилагательное: «низкий» что? Здесь низкая именно позиция, а не значение.

### Почему условие цикла нестрогое

`while (lowIndex <= highIndex)`, а не `<`.

Условие цикла — это ответ на вопрос «когда работа ещё НЕ закончена» (приём 1 из [`heuristics.md`](../../heuristics.md)). Работа не закончена, пока на участке остался хоть один непроверенный элемент. Границы включительные, поэтому при `lowIndex == highIndex` такой элемент есть — ровно один, и он ещё ни разу не сравнивался с `target`.

Со строгим `<` этот последний элемент остался бы непросмотренным. На массиве из одного элемента (пример 3) цикл не начался бы вовсе, и метод вернул бы `-1` при верном ответе `0`.

Обратная сторона: раз при равных границах цикл ещё раз входит в тело, он обязан на этой итерации что-то изменить, иначе повторит то же самое навсегда. Об этом — следующий раздел.

### Почему границы сдвигаются на единицу

`lowIndex = middleIndex + 1`, а не `lowIndex = middleIndex`.

Средний элемент к этому моменту **уже сравнён** с `target` и заведомо не равен ему. Значит его можно исключить вместе с половиной, и единица — не «поправка на всякий случай», а точное описание того, что мы про него узнали.

Без единицы алгоритм зависает. Проверка на массиве `[1, 2]` и `target = 2`:

```
lowIndex = 0, highIndex = 1
middleIndex = (0 + 1) / 2 = 0            целочисленное деление
nums[0] = 1 < 2   значит  lowIndex = middleIndex = 0
```

Границы не изменились, следующая итерация повторит те же вычисления — цикл вечный. Единица гарантирует, что участок уменьшается **на каждой** итерации, и это же гарантирует завершаемость.

С правой границей то же самое, только пример короче. Пусть `highIndex = middleIndex` (без единицы), массив `[1]`, `target = 0`: середина равна 0, значение `1` больше искомого, правая граница получает 0 — то есть остаётся на месте. Участок `[0..0]` не пустеет, и цикл снова вечный.

Общее правило для обеих границ одно: проверенный элемент выбрасывается. Это и есть **приём 9** из [`heuristics.md`](../../heuristics.md) — каждая итерация обязана уменьшать задачу.

### Запись середины

Середина считается обычной полусуммой:

```java
int middleIndex = (lowIndex + highIndex) / 2;
```

Массив не длиннее `10^4` элементов, значит индексы не больше 9 999, а их сумма — не больше двадцати тысяч. До потолка `int` отсюда далеко, поэтому никакой защиты полусумме не требуется.

Существует другая запись, `lowIndex + (highIndex - lowIndex) / 2`, — она нужна там, где границы могут дорасти до миллиарда. К этой задаче отношения не имеет, разбор вынесен в конец файла, в раздел «Дополнение».

### Отсортированность не проверяется — и это осознанно

Метод не убеждается, что вход отсортирован. Причина арифметическая: проверка потребовала бы прохода по всему массиву, то есть `O(n)`, и съела бы весь выигрыш от `O(log n)`. Смысла в алгоритме за логарифм, которому предшествует линейная проверка, нет.

Поэтому отсортированность — **предусловие**: обязательство вызывающей стороны, а не то, что метод контролирует. На неотсортированном входе метод не упадёт и не зациклится, он просто вернёт неверный ответ, — и это ещё одна причина проговорить предусловие вслух на собеседовании.

Термин — в [`docs/glossary.md`](../../glossary.md).

### Ловушка: `-1` как ответ и `-1` как индекс

Возврат `-1` означает «не найдено» и никогда не означает позицию. Это работает потому, что индексы неотрицательны, то есть `-1` заведомо не пересекается ни с одним корректным ответом.

Стандартный `Arrays.binarySearch` устроен иначе: при неудаче он возвращает `-(точка вставки) - 1`, то есть отрицательное число, из которого ещё можно вытащить, **куда** элемент следовало бы вставить. Проверено запуском:

```
Arrays.binarySearch([-1, 0, 3, 5, 9, 12], 9)  ->   4     нашёл, индекс 4
Arrays.binarySearch([-1, 0, 3, 5, 9, 12], 2)  ->  -3     не нашёл, вставлять на позицию 2
Arrays.binarySearch([2, 4, 6, 8], 9)          ->  -5     не нашёл, вставлять на позицию 4
```

Формула разворачивается обратно как `точка вставки = -(результат) - 1`. Единица в ней нужна ровно потому, что без неё точка вставки 0 дала бы `-0`, то есть ноль, — а ноль уже занят под «нашёл в самом начале».

Задача 35 (Search Insert Position) как раз про эту точку вставки, и решается она тем же циклом: ответом становится позиция, на которой границы разошлись.

### Сколько шагов делает поиск

#### Что такое `log₂ n`

Логарифм — это **показатель степени**. Возводится основание, а логарифм отвечает на вопрос «в какую степень».

```
log₂ n = такое k, что 2ᵏ = n
```

Основание логарифма и основание степени — одно и то же число, двойка. Искомое — показатель `k`.

| `n` | `log₂ n` | потому что |
|---|---|---|
| 8 | 3 | `2³ = 8` |
| 10 | ≈ 3,32 | `2³ = 8` мало, `2⁴ = 16` много — показатель между тремя и четырьмя |
| 16 | 4 | `2⁴ = 16` |
| 1 000 | ≈ 9,97 | `2¹⁰ = 1024`, чуть больше тысячи |
| 1024 | 10 | `2¹⁰ = 1024` |

#### Откуда логарифм берётся в бинарном поиске

Каждое деление сжимает участок вдвое, значит после `k` делений он меньше исходного в `2ᵏ` раз. Делить становится нечего, когда от `n` элементов остаётся один:

```
n / 2ᵏ = 1    значит    2ᵏ = n    значит    k = log₂ n
```

Разбор записи по частям:

- `2ᵏ` — во сколько раз сжался участок. После первого деления он меньше в два раза, после второго в четыре, после третьего в восемь; после `k` делений — в `2ᵏ`.
- `n / 2ᵏ` — сколько элементов осталось: начали с `n`, уменьшили в `2ᵏ` раз.
- `= 1` — условие остановки: остался один элемент, делить дальше нечего.

Целиком запись читается так: «после `k` делений от `n` элементов остался один».

Наглядно, `n = 1000`:

| Делений | Расчёт | Осталось элементов |
|---|---|---|
| 0 | `1000 / 2⁰ = 1000 / 1 = 1000` | 1000 |
| 1 | `1000 / 2¹ = 1000 / 2 = 500` | 500 |
| 2 | `1000 / 2² = 1000 / 4 = 250` | 250 |
| 3 | `1000 / 2³ = 1000 / 8 = 125` | 125 |
| 4 | `1000 / 2⁴ = 1000 / 16 ≈ 62` | 62 |
| 5 | `1000 / 2⁵ = 1000 / 32 ≈ 31` | 31 |
| 6 | `1000 / 2⁶ = 1000 / 64 ≈ 15` | 15 |
| 7 | `1000 / 2⁷ = 1000 / 128 ≈ 7` | 7 |
| 8 | `1000 / 2⁸ = 1000 / 256 ≈ 3` | 3 |
| 9 | `1000 / 2⁹ = 1000 / 512 ≈ 1` | 1 — остался один элемент |

Числа в правой колонке совпадают с длинами участков в трассировке из `main`: после первого деления там `[500..999]`, после четвёртого `[938..999]`, после девятого `[999..999]`.

Дальше уравнение решается умножением обеих частей на `2ᵏ`: из `n / 2ᵏ = 1` получается `n = 2ᵏ`, а `k = log₂ n` — уже по определению логарифма.

#### Делений девять, а итераций десять

Два счёта легко перепутать, и они дают разные числа.

`log₂ n` считает **деления**: таблица выше сжала тысячу до одного элемента за девять делений, и `log₂ 1000 ≈ 9,97` — про них.

Цикл считает **сравнения**, и их на одно больше. Каждое деление происходит после сравнения, которое ответа не дало; когда делить стало нечего, единственный оставшийся элемент всё ещё надо сравнить с `target`. Это сравнение и есть десятое.

```
девять сравнений        участок сузился с 1000 до 1 элемента
десятое сравнение       проверили последний оставшийся элемент
```

Поэтому в формуле числа итераций стоит `+ 1`: `⌊log₂ n⌋ + 1`. Трассировка в `main` на тысяче элементов печатает ровно десять шагов.

#### Сколько это на практике

Число итераций в худшем случае — `⌊log₂ n⌋ + 1`.

| Длина массива | Худшее число итераций | ближайшая степень двойки |
|---|---|---|
| 10 | 4 | `2³ = 8`, `2⁴ = 16` |
| 1 000 | 10 | `2¹⁰ = 1024` |
| 10 000 (предел условия) | 14 | `2¹³ = 8192`, `2¹⁴ = 16 384` |
| 1 000 000 | 20 | `2²⁰ = 1 048 576` |

Это же число можно увидеть своими глазами: в конце `main` класс печатает трассировку — каждый шаг с границами участка и серединой, а в конце «найдено на шаге N» или «не найдено, потрачено шагов N». Печать живёт в отдельном методе `searchWithStepLog`; само решение остаётся чистой функцией, а тест сверяет, что оба дают один ответ. На тысяче элементов трассировка показывает ровно десять шагов.

Обратный ход тот же: удвоили массив — умножили `n` на два — показателю прибавилась единица. Отсюда практический вывод для собеседования: **удвоение входа стоит одного лишнего шага**, и именно это означает запись `O(log n)`.

Про то, почему в записи `O(log n)` основание не указывают и когда оно всё-таки важно, — [`docs/glossary.md`](../../glossary.md), раздел про O-нотацию.

### Разбор по шагам

Пример 1, `nums = [-1, 0, 3, 5, 9, 12]`, `target = 9`:

```
индексы:   0   1   2   3   4   5
nums:     -1   0   3   5   9  12

шаг 1:  lowIndex = 0, highIndex = 5, middleIndex = 2, nums[2] = 3
        3 < 9   значит  участок [3..5], lowIndex = 3
шаг 2:  lowIndex = 3, highIndex = 5, middleIndex = 4, nums[4] = 9
        совпало   значит  ответ 4
```

Пример 2, тот же массив, `target = 2` — случай «не найдено»:

```
шаг 1:  lowIndex = 0, highIndex = 5, middleIndex = 2, nums[2] = 3
        3 > 2   значит  участок [0..1], highIndex = 1
шаг 2:  lowIndex = 0, highIndex = 1, middleIndex = 0, nums[0] = -1
        -1 < 2  значит  участок [1..1], lowIndex = 1
шаг 3:  lowIndex = 1, highIndex = 1, middleIndex = 1, nums[1] = 0
        0 < 2   значит  участок [2..1], lowIndex = 2
        границы разошлись, цикл кончился, ответ -1
```

Обрати внимание на шаг 3: он состоялся только благодаря нестрогому условию. Со строгим `<` цикл закончился бы сразу после шага 2, потому что границы к этому моменту равны (`1` и `1`). Ячейка с индексом 1 осталась бы непроверенной. Ответ здесь вышел бы тот же самый, `-1`, но по случайности: в ячейке лежит `0`, а искали `2`. Стой там двойка — метод соврал бы.

## Свойства решения

Что означает каждая строка — в [`docs/algorithm-properties.md`](../../algorithm-properties.md).

| Характеристика | Значение |
|---|---|
| Время в худшем случае | `O(log n)` — участок делится пополам, пока не станет пустым; худший случай это и «не найдено», и находка на последнем шаге |
| Время в лучшем случае | `O(1)` — `target` оказался ровно посередине и нашёлся первым же сравнением |
| Память | `O(1)` — две границы, середина и её значение; рекурсии нет, стек не растёт |
| Проходов по входу | ни одного полного: читается не больше `log₂ n + 1` элементов |
| Ранний выход | да, находка возвращается прямо из цикла |
| Изменяет ли вход | нет, массив только читается |
| Требования к входу | отсортирован по возрастанию — предусловие, метод его не проверяет |
| Работа на потоке | нет: нужен доступ к произвольному индексу, а поток даёт элементы по очереди |
| Детерминированность | да |
| Завершаемость | каждая итерация уменьшает участок минимум на один элемент за счёт `+1` / `−1` в сдвигах |
| Устойчивость к деградации | при `n = 10^4` лучший случай — 1 сравнение, худший — 14; деградировать здесь почти некуда |
| Поведение на вырожденных входах | самый короткий вход по условию — массив из одного элемента, он обрабатывается циклом наравне с остальными; пустого массива и `null` условие не допускает, поэтому охранных проверок в решении нет |

Для сравнения: линейный проход `O(n)` на предельных `10^4` элементах сделал бы до 10 000 сравнений против 14 у бинарного поиска.

## Приёмы из шпаргалки

- **Приём 1** (как придумать условие цикла): «работа не закончена, пока остался непроверенный элемент» — отсюда нестрогое `<=`.
- **Приём 3** («для всех» против «существует»): задача про существование, поэтому находка возвращается изнутри цикла, а `-1` — после него, фолбэком.
- **Приём 9** (каждая итерация обязана уменьшать задачу): единицы в сдвигах границ — не украшение, без них цикл вечный.

Отличие книжного кода от нашего одно, сверено с оригиналом PDF, а не только с распознанным текстом:

| В книге | Здесь | Почему |
|---|---|---|
| порядок веток: сначала `<`, потом `>`, совпадение последним | сначала совпадение, потом `<` и `>` | совпадение — это выход из метода, и его удобнее видеть первым; на число сравнений порядок не влияет |

Полусумма у Макдауэлл записана как `mid = (low + high) / 2` — так же, как здесь.

Рекурсивный вариант из книги здесь не воспроизводится: он делает ровно то же самое, но тратит `O(log n)` стека вместо `O(1)`.

## Дополнение: от чего страхует запись середины

К решению задачи 704 этот раздел отношения не имеет: там стоит обычная полусумма, и ограничения — массив до `10^4` элементов — переполнение исключают полностью. Речь ниже о другой записи, `lowIndex + (highIndex - lowIndex) / 2`, — на случай, если про неё спросят на собеседовании или она встретится в чужом коде.

### Ход мысли

Отправная точка — запрет, а не преобразование формулы. Переполниться может ровно одно место, сложение двух индексов, значит складывать их нельзя. Что тогда можно посчитать безопасно? Расстояние между границами `highIndex - lowIndex`: оно заведомо не больше `highIndex`, а `highIndex` — корректный индекс.

Дальше остаётся вернуться от расстояния к позиции: половина расстояния — это сдвиг от левой границы до середины, и его прибавляют к `lowIndex`. Порядок именно такой — **сначала вычитание**, потому что оно безопасно, и только потом прибавление `lowIndex`.

### Почему обе записи дают одно число

Проверка задним числом. Обозначим расстояние `d = highIndex - lowIndex`:

- разностная форма даёт `lowIndex + ⌊d / 2⌋`;
- школьная даёт `⌊(lowIndex + highIndex) / 2⌋ = ⌊(2 · lowIndex + d) / 2⌋ = ⌊lowIndex + d / 2⌋`.

`lowIndex` — целое число, поэтому его можно вынести из-под округления: `⌊lowIndex + d / 2⌋ = lowIndex + ⌊d / 2⌋`. Записи сходятся, целочисленное деление ничего не портит. Верно это при `highIndex >= lowIndex`, то есть ровно тогда, когда цикл выполняется.

На числах: `lowIndex = 2`, `highIndex = 5`. Школьная — `(2 + 5) / 2 = 3`. Разностная — `2 + (5 - 2) / 2 = 3`.

### Где школьная запись ломается

Числа получены прогоном на JDK 25. Граница проходит между первой и второй строкой:

| `lowIndex` | `highIndex` | `lowIndex + highIndex` | школьная | разностная |
|---|---|---|---|---|
| 1 073 741 823 | 1 073 741 824 | 2 147 483 647 | 1 073 741 823 | 1 073 741 823 |
| 1 073 741 824 | 1 073 741 824 | −2 147 483 648 | −1 073 741 824 | 1 073 741 824 |

В первой строке сумма равна в точности максимуму `int`. Во второй левый индекс больше на единицу, сумма перешагивает максимум и продолжается с минимума — середина уходит в минус, и `nums[middleIndex]` даёт `ArrayIndexOutOfBoundsException`. Оба индекса при этом нормальные, а участок состоит из одного элемента.

Чтобы такое случилось, массив должен быть длиннее `2^30` элементов, то есть занимать больше четырёх гигабайт. Практически же формула нужна не на массивах, а на бинарном поиске **по диапазону значений**, где границами служат сами числа: там миллиард достигается без всякой памяти.

### Запись из JDK

В стандартной библиотеке (`java.base/java/util/Arrays.java`, метод `binarySearch0`) середина считается беззнаковым сдвигом:

```java
int mid = (low + high) >>> 1;
```

Сумма переполняется точно так же, но результат верен: биты остаются правильными, портится только их истолкование — старший бит начинает читаться как знак. Беззнаковый сдвиг `>>>` вдвигает слева ноль и читает те же биты как неотрицательное число.

Наивная запись `(low + high) / 2` десятилетиями стояла в учебниках и в самом JDK. Ошибку описал Джошуа Блох в 2006 году; по его словам, баг прожил в стандартной библиотеке около девяти лет — чтобы его увидеть, нужен массив больше миллиарда элементов.
