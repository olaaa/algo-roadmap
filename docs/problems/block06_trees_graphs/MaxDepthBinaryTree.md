# 104. Maximum Depth of Binary Tree

*Максимальная глубина двоичного дерева*

**Сложность:** Easy · **Паттерн:** обход в глубину рекурсией · **Класс:** `block06_trees_graphs.MaxDepthBinaryTree`

## Условие

Дан корень двоичного дерева. Вернуть его максимальную глубину.

Максимальная глубина — это **число узлов** на самом длинном пути от корня до листа. Считаются именно узлы, а не переходы между ними: у дерева из одного узла глубина равна единице.

Лист — узел, у которого нет ни левого, ни правого потомка.

Поддерево узла — сам этот узел и всё, что растёт из него вниз: его потомки, потомки потомков и так далее до листьев. Это тоже двоичное дерево, только корнем у него стоит выбранный узел. У каждого узла два поддерева — левое (растёт из `left`) и правое (из `right`); отсутствующий потомок даёт пустое поддерево. В примере 1 левое поддерево корня — один узел `9`, правое — `20` с потомками `15` и `7`. Термин есть в [словарике](../../glossary.md#поддерево).

## Примеры

### Пример 1

```
Вход:  root = [3, 9, 20, null, null, 15, 7]

        3
       / \
      9   20
         /  \
        15   7

Выход: 3
```

Самый длинный путь — `3 → 20 → 15` (или `3 → 20 → 7`), в нём три узла.

Как читается сама запись `[3, 9, 20, null, null, 15, 7]` — в [`TreeNotation.md`](TreeNotation.md). Коротко: это обход в ширину слева направо, где у каждого непустого узла записаны оба потомка; арифметические формулы `2i + 1` к этой записи не применимы.

### Пример 2

```
Вход:  root = [1, null, 2]

        1
         \
          2

Выход: 2
```

### Пример 3

```
Вход:  root = []
Выход: 0
```

Пустое дерево — законный вход по ограничениям, и глубина у него нулевая.

### Пример 4

```
Вход:  root = [7]
Выход: 1
```

Один узел, он же корень и лист.

## Ограничения

- число узлов в дереве — от `0` до `10^4`
- `-100 <= Node.val <= 100`

## Почему такие ограничения

Ноль узлов разрешён, поэтому `root == null` — **не край, который надо отсечь охранной проверкой, а обычный вход** с ответом `0`.

Верхняя граница важнее, чем кажется. Десять тысяч узлов могут выстроиться в цепочку — дерево, где у каждого узла ровно один потомок. Тогда глубина рекурсии равна числу узлов, и вопрос «выдержит ли стек» становится частью задачи, а не отвлечённым рассуждением. Проверено тестом: цепочка из `10 000` узлов проходит.

Диапазон значений узлов на решение не влияет вовсе: значения не сравниваются и не складываются, важна только форма дерева.

## Идея решения

Глубина дерева выражается через глубину его поддеревьев: **глубина дерева с корнем в узле на единицу больше, чем у более глубокого из двух его поддеревьев**.

Речь именно о глубине дерева, растущего из узла вниз, а не о глубине самого узла — та считается от корня всего дерева и у поддеревьев, наоборот, больше. Разница терминов разобрана ниже, в разделе про глубину, высоту и уровень.

Это определение сразу превращается в рекурсию:

```java
public static int maxDepth(TreeNode root) {
    if (root == null) {
        return 0;
    }
    int leftDepth = maxDepth(root.left);
    int rightDepth = maxDepth(root.right);
    return 1 + Math.max(leftDepth, rightDepth);
}
```

Рекурсия здесь не приём для сокращения кода, а прямая запись структуры: дерево состоит из узла и двух деревьев поменьше, и тот же вопрос задаётся каждому из них.

### Что делает каждая переменная

| Переменная | Что хранит | Зачем она нужна |
|---|---|---|
| `root` | корень дерева, глубина которого сейчас считается | на каждом уровне рекурсии это свой узел, а не только корень всего дерева; имя пришло из условия LeetCode |
| `leftDepth` | глубину левого поддерева, то есть высоту левого потомка | результат рекурсивного спуска налево; честнее было бы `leftHeight`, см. раздел «Почему задача про глубину, а код считает высоту» |
| `rightDepth` | глубину правого поддерева, то есть высоту правого потомка | результат спуска направо; то же про имя |

Обе переменные можно было не заводить и написать `1 + Math.max(maxDepth(root.left), maxDepth(root.right))`. Смысл тот же; отдельные имена оставлены потому, что в них видно главное — метод спускается **дважды**, и на каждой ветке результат свой.

### Почему `null` — это базовый случай, а не охранная проверка

Проверка на `null` выглядит как та самая охранная, которых в проекте не бывает. Но здесь она делает две содержательные вещи:

1. отвечает на **законный вход** — пустое дерево, у которого глубина равна нулю;
2. **останавливает рекурсию**: без неё спуск не закончился бы никогда.

Вторая роль важнее. У рекурсии обязан быть случай, в котором она не вызывает себя, — иначе стек переполнится. Здесь такой случай — отсутствующий потомок, и `null` его и обозначает.

### Почему единица прибавляется снаружи `Math.max`

Единица — это **сам текущий узел**. Он добавляется к пути один раз, независимо от того, какое поддерево оказалось глубже.

Если написать `Math.max(1 + leftDepth, 1 + rightDepth)`, ответ получится тот же, но запись хуже: единица размножилась, хотя узел по-прежнему один. Порядок «сначала выбрать глубже, потом прибавить себя» точнее описывает определение глубины.

### Разбор по шагам

Пример 1, дерево `[3, 9, 20, null, null, 15, 7]`. Рекурсия идёт сверху вниз, а ответы собираются снизу вверх:

```
maxDepth(3)
├── maxDepth(9)
│   ├── maxDepth(null) → 0
│   └── maxDepth(null) → 0
│   вернул 1 + max(0, 0) = 1
└── maxDepth(20)
    ├── maxDepth(15) → 1
    └── maxDepth(7)  → 1
    вернул 1 + max(1, 1) = 2
вернул 1 + max(1, 2) = 3
```

Обрати внимание на направление: **вниз идут вызовы, вверх возвращаются числа**. Узел не может ответить, пока не ответили оба его потомка.

### Глубина, высота и уровень — три похожих термина

Слова путаются, и на собеседовании их стоит различать.

| Термин | Про что | Пример на дереве из примера 1 |
|---|---|---|
| глубина узла | сколько узлов от корня до него | у `15` глубина 3 |
| высота узла | сколько узлов от него до самого дальнего листа | у `20` высота 2 |
| высота дерева | высота корня | 3 |
| уровень | все узлы одной глубины | уровень 2 — это `9` и `20` |

LeetCode считает глубину в узлах — это видно по примеру 4. Учебники считают в рёбрах, и там все числа на единицу меньше; разница разобрана в [`BinaryTree.md`](../../datastructures/BinaryTree.md), раздел «Счёт в рёбрах: как в учебниках». На собеседовании стоит проговорить, что именно считается, до того как писать код.

### Почему задача про глубину, а код считает высоту

Название задачи описывает **результат**: найти самый глубокий лист и назвать его глубину. Это взгляд сверху вниз, от корня.

Рекурсивный код считает **снизу вверх**: лист отвечает 1, родитель берёт большее из ответов потомков и прибавляет себя. По определению это высота узла — путь от листа к узлу. `maxDepth(root.left)` возвращает высоту левого потомка, а не его глубину: глубина левого потомка всегда 2, а метод возвращает 1 для листа и больше для поддерева поглубже.

Число одно, потому что глубина самого глубокого листа и высота корня — один и тот же путь, только пройденный с разных концов. У дерева целиком «максимальная глубина» и «высота» — синонимы; у Кормена и у Макдауэлл та же величина называется высотой дерева. LeetCode назвал задачу по результату, а решение естественно пишется через высоту — отсюда и ощущение, что название не сходится с кодом.

Честнее было бы назвать переменные `leftHeight` и `rightHeight`: они хранят именно высоты поддеревьев. В коде оставлены `leftDepth` и `rightDepth` — вслед за именем метода `maxDepth`, которое пришло из условия и менять его нельзя.

Название задачи буквально ложится на другое решение — итеративное, на стеке (см. «Дополнение: тот же обход на явном стеке» ниже). Оно идёт **сверху вниз**, несёт глубину каждого узла с собой и берёт наибольшую из них: там считается именно глубина, и слово «максимальная» относится к ней. Одна величина, два способа её посчитать, и у каждого способа своё родное слово: рекурсия — высота, стек — глубина.

## Дополнение: где ломается рекурсия

К решению задачи это отношения не имеет — ограничения условия рекурсия выдерживает.

Каждый вложенный вызов занимает кадр в стеке потока, а размер стека ограничен (по умолчанию около мегабайта, настраивается флагом `-Xss`). Проверка на JBR 25 с настройками по умолчанию:

| Длина цепочки | Результат |
|---|---|
| 10 000 (предел условия) | глубина посчитана |
| 20 000 | `StackOverflowError` |

То есть запас есть, но небольшой — примерно вдвое. Если бы в условии стояло `10^5` узлов, рекурсивное решение пришлось бы заменить на обход с явной структурой данных: очередью по уровням или стеком. Вариант со стеком разобран ниже.

## Дополнение: тот же обход на явном стеке

К решению задачи это отношения не имеет — по ограничениям рекурсии хватает. Класс `MaxDepthBinaryTreeIterative` делает то же самое без рекурсии; тесты у него те же, плюс цепочка из `20 000` узлов, на которой рекурсивный вариант падает.

### Откуда берётся стек

Рекурсивный `maxDepth` сам ничего не запоминает — за него это делает стек вызовов. Когда метод вызывает себя для `root.left`, кадр с текущим узлом остаётся лежать в стеке вызовов и ждёт, пока вложенный вызов вернёт число. В каждый момент в этом стеке лежит **путь от корня до текущего узла**: корень внизу, текущий узел наверху. Поэтому у рекурсии глубина узла нигде не хранится явно — она равна числу кадров в стеке.

Убрать рекурсию — значит завести такой стек самим. Но в явный стек кладут не путь, а **узлы, которые ещё предстоит посетить**: сняли узел — положили его потомков. Это другое содержимое. В стеке вызовов лежали предки одного узла, здесь лежат отложенные узлы с разных уровней: например, правый потомок корня может ждать в стеке, пока обход спускается по левому поддереву на десять уровней вниз.

Из-за этого теряется то, что у рекурсии было бесплатно: снятому узлу глубину взять неоткуда. Ни размер стека, ни положение узла в нём её не показывают. Поэтому глубину кладут в стек **вместе с узлом**: у корня она `1`, у потомков — на единицу больше, чем у родителя. Узел приносит свою глубину с собой, и когда его снимают, она уже известна.

Отсюда второе отличие от рекурсии. Рекурсивный метод считал глубину **снизу вверх**: узел не мог ответить, пока не ответили оба потомка, и ответ собирался при возврате. Здесь глубина узла известна **в момент снятия**, ни от каких потомков она не зависит. Значит, к снятому узлу возвращаться не нужно, и ответ — просто наибольшая из глубин, которые прошли через стек.

```java
private record NodeAtDepth(TreeNode node, int depth) {
}

public static int maxDepth(TreeNode root) {
    if (root == null) {
        return 0;
    }

    Deque<NodeAtDepth> nodesToVisit = new ArrayDeque<>();
    nodesToVisit.push(new NodeAtDepth(root, 1));

    int maxDepth = 0;
    while (!nodesToVisit.isEmpty()) {
        NodeAtDepth current = nodesToVisit.pop();
        maxDepth = Math.max(maxDepth, current.depth());

        int childDepth = current.depth() + 1;
        if (current.node().right != null) {
            nodesToVisit.push(new NodeAtDepth(current.node().right, childDepth));
        }
        if (current.node().left != null) {
            nodesToVisit.push(new NodeAtDepth(current.node().left, childDepth));
        }
    }
    return maxDepth;
}
```

Каждая итерация цикла делает три действия, всегда одни и те же:

1. **снять** с вершины стека узел вместе с его глубиной;
2. **учесть** эту глубину в ответе — если она больше `maxDepth`, запомнить её;
3. **положить** в стек потомков снятого узла, каждого с глубиной `childDepth`, то есть на единицу больше, чем у снятого.

Цикл продолжается, пока стек не опустеет. Опустеет он ровно тогда, когда у всех снятых узлов потомки тоже сняты, — то есть когда пройдено всё дерево.

Правый потомок кладётся раньше левого, чтобы левый оказался сверху и снялся первым: спуск идёт влево, как у рекурсии, и порядок посещения узлов совпадает с прямым обходом (pre-order) из [`BinaryTree.md`](../../datastructures/BinaryTree.md). Для ответа этот порядок не важен — максимум не зависит от того, в какой последовательности сравнивались глубины, — но одинаковый с рекурсией порядок проще проверять и сравнивать.

### Разбор по шагам

Пример 1, дерево `[3, 9, 20, null, null, 15, 7]`. В столбце «стек после итерации» вершина стека записана **слева**: это тот элемент, который снимется следующим.

| Итерация | Снято (узел, глубина) | `maxDepth` после | Положено | Стек после итерации |
|---|---|---|---|---|
| до цикла | — | 0 | (3, 1) | (3, 1) |
| 1 | (3, 1) | 1 | (20, 2), затем (9, 2) | (9, 2), (20, 2) |
| 2 | (9, 2) | 2 | потомков нет | (20, 2) |
| 3 | (20, 2) | 2 | (7, 3), затем (15, 3) | (15, 3), (7, 3) |
| 4 | (15, 3) | 3 | потомков нет | (7, 3) |
| 5 | (7, 3) | 3 | потомков нет | пусто |

Стек пуст, цикл закончился, ответ `3`. Итераций ровно пять — по числу узлов: каждый узел один раз попал в стек и один раз был снят.

На что смотреть в таблице:

- **Глубина приходит вместе с узлом.** В итерации 3 узел `20` снимается с глубиной `2`, хотя его положили ещё в итерации 1. Всё время, пока обход был занят узлом `9`, запись `(20, 2)` лежала в стеке и хранила свою глубину. Без этого числа в итерации 3 пришлось бы заново выяснять, на каком уровне стоит `20`.
- **Размер стека не равен глубине.** После итерации 1 в стеке два элемента, а глубина снятого узла — `1`. После итерации 4 в стеке один элемент, а глубина — `3`. Это первая из двух ошибок, разобранных ниже.
- **Ответ растёт только в момент снятия.** `maxDepth` меняется в итерациях 1, 2 и 4 — когда снимается узел глубже всех предыдущих. В итерациях 3 и 5 снятая глубина не больше текущего ответа, и он остаётся прежним.
- **Возвратов нет.** У рекурсии на этом же дереве узел `3` получал ответ последним, после того как ответили `9` и `20` (см. разбор по шагам выше, в основном решении). Здесь узел `3` учтён первым и больше не нужен: его глубина `1` в ответ уже попала.

### Что делает каждая переменная

| Переменная | Что хранит | Зачем она нужна |
|---|---|---|
| `NodeAtDepth` | запись из двух полей: узел и его глубина | элемент стека — узел с глубиной; без глубины снятый узел не знал бы, на каком уровне стоит |
| `nodesToVisit` | стек записей `NodeAtDepth`, которые ещё предстоит снять | замена стека вызовов; `Deque` с `push` и `pop` — снимается последняя положенная запись |
| `current` | запись `NodeAtDepth`, снятая на этой итерации | её глубина идёт в ответ, её потомки — в стек |
| `childDepth` | глубина потомков `current` | на единицу больше глубины родителя; посчитана один раз на обоих потомков |
| `maxDepth` | наибольшая глубина среди снятых записей | ответ; обновляется при каждом снятии |

### Две ошибки, которые здесь легко сделать

Считать глубиной размер стека. У рекурсии размер стека вызовов и был глубиной, потому что там лежал путь от корня. Здесь в стеке лежат отложенные узлы разных уровней: в дереве `[1, 2, 3]` после снятия `1` в стеке два узла глубины `2`, а на цепочке в стеке всегда один узел, хотя глубина растёт. Размер стека ничего не говорит о глубине.

Хранить глубину в карте по `node.val`. Значения узлов не уникальны — тест `[-100, 100, -100]` это проверяет, — и два узла с одинаковым значением затирали бы друг друга. Ключом может быть сам узел (`TreeNode` сравнивается по ссылке), но карта на все узлы — это `O(n)` памяти против `O(h)` у стека записей `NodeAtDepth`, поэтому глубина внутри элемента стека лучше.

### Свойства решения на стеке

| Характеристика | Значение |
|---|---|
| Время | `O(n)`: каждый узел один раз кладётся в стек и один раз снимается |
| Память | `O(h)`: в стеке одновременно не больше `h + 1` записей — по одному отложенному правому потомку на каждый уровень текущего пути от корня. Куча, а не стек потока, поэтому `-Xss` не ограничивает |
| Порядок обхода | прямой (pre-order): глубина узла учитывается при снятии, до потомков. Рекурсивный вариант, наоборот, складывает ответ при возврате — обратный порядок; здесь это не нужно, потому что глубина узла известна заранее, а не считается из потомков |
| Поведение на вырожденных входах | пустое дерево — `0`; цепочка из `20 000` узлов проходит, у рекурсии на ней `StackOverflowError` |
