# 1. Two Sum
*Сумма двух чисел*

**Сложность:** Easy · **Паттерн:** хеш-таблица за один проход · **Класс:** `block03_hashtables.TwoSum`

## Условие

Дан массив целых чисел `nums` (в произвольном, **не** отсортированном порядке) и число `target`. Нужно найти два таких элемента, сумма которых равна `target`, и вернуть их индексы — `[index1, index2]`, нумерация **0-based** (первый элемент имеет индекс 0).

Гарантируется, что **ровно одно** решение существует. Один и тот же элемент (одну и ту же позицию) нельзя использовать дважды. Порядок индексов в ответе не важен.

Это задача №1 на LeetCode — именно с неотсортированным массивом и возвратом индексов в исходном порядке. Поэтому два указателя тут в лоб не годятся (они требуют сортировки, а сортировка потеряет исходные индексы), и эталонный ответ — HashMap.

## Примеры

### Пример 1

```
Вход:  nums = [2, 7, 11, 15], target = 9
Выход: [0, 1]
```

`nums[0] + nums[1] = 2 + 7 = 9`.

### Пример 2

```
Вход:  nums = [3, 2, 4], target = 6
Выход: [1, 2]
```

`nums[1] + nums[2] = 2 + 4 = 6`. Обрати внимание: `nums[0] = 3` не подходит в пару сам с собой (`3 + 3`), потому что позицию нельзя использовать дважды.

### Пример 3

```
Вход:  nums = [3, 3], target = 6
Выход: [0, 1]
```

Два одинаковых значения на **разных** позициях — валидная пара.

## Ограничения

- `2 <= nums.length <= 10^4`
- `-10^9 <= nums[i] <= 10^9`
- `-10^9 <= target <= 10^9`
- существует ровно одно решение

## Почему такие ограничения

Длина `≤ 10^4` невелика: даже наивный O(n²) при n = 10⁴ даёт n² = 10⁸ операций — на грани секундного лимита, поэтому brute force «проходит впритык», а O(n) через HashMap отрабатывает с колоссальным запасом. То есть предел подобран так, что квадрат ещё не падает, но и не поощряется.

Диапазон `nums[i]` тут широкий — до `10^9` по модулю. Сумма двух элементов может достигать `2 * 10^9`, а это уже **больше** границы int (`≈ 2,15 * 10^9` только-только вмещает `2 * 10^9`, а `2 * 10^9` ещё влезает, но запас крошечный). На практике для Two Sum это не мешает, потому что мы считаем `complement = target - nums[i]` — разность, а не сумму, и она всегда в пределах диапазона входных чисел. Но если бы где-то складывали два `nums[i]` напрямую (как в brute force `nums[firstIndex] + nums[secondIndex]`), на таких границах стоило бы держать в голове риск переполнения int. В наших тестах числа маленькие, так что вопрос чисто теоретический.

## Идея решения

Массив не отсортирован, сортировать нельзя (потеряем индексы) — значит два указателя не подходят. Разменяем память на скорость.

Идём одним проходом слева направо и держим `HashMap`: `виденное число -> его индекс`. Для текущего элемента считаем `complement = target - nums[currentIndex]` — какое число нужно в пару. Если это дополнение уже лежит в map (то есть встречалось раньше, левее) — пара найдена, возвращаем его индекс и текущий. Если нет — кладём текущее число в map и идём дальше.

Три момента, которые стоит проговорить на собеседовании:

1. **Кладём в map ПОСЛЕ проверки, а не до.** Так элемент гарантированно не спарится сам с собой: в момент проверки в map лежат только элементы левее текущего.
2. **Trade-off время ↔ память.** Наивный перебор всех пар — O(n²) времени, O(1) памяти. HashMap — O(n) времени ценой O(n) памяти. Классический размен.
3. **Чем отличается от двух указателей.** Двум указателям нужен отсортированный массив (и они дают O(1) памяти), а тут массив неупорядочен и важны исходные индексы — поэтому именно HashMap.

## Свойства решений

| Характеристика | `HashMap` (эталон) | Перебор пар (baseline) |
|---|---|---|
| Время, худший случай | `O(n)` в среднем | `O(n²)` |
| Время, лучший случай | `O(1)` — пара нашлась на втором элементе | `O(1)` — пара нашлась на первой проверке |
| Память | `O(n)` — до `n` записей «число → индекс» | `O(1)` — только индексы |
| Проходов по входу | один | до `n` проходов, вложенный цикл |
| Ранний выход | есть: `return` сразу, как дополнение найдено в карте | есть, там же |
| Изменяет ли вход | нет | нет |
| Требования к входу | никаких: сортировать нельзя, иначе потеряются исходные индексы | никаких |
| Работа на потоке | да по природе: решение принимается по уже виденному, заглядывать вперёд не нужно. Потоковой версии в классе нет | нет: перебор возвращается к прошлым элементам |
| Детерминированность | да | да |
| Устойчивость к деградации | `O(1)` у `HashMap` — амортизированная оценка, при массовых коллизиях деградирует; см. [`Pattern_HashMap.md`](Pattern_HashMap.md) | худшего случая нет, он и так квадратичный |
| Порядок операций | элемент кладётся в карту ПОСЛЕ проверки, иначе он спарится сам с собой | сравниваются заведомо разные индексы |
| Фолбэк после цикла | по условию решение существует; если пары нет, метод возвращает `{-1, -1}` — ветку всё равно надо покрыть тестом | то же |

Классический размен: перебор экономит память, `HashMap` экономит время. При `n = 10^4` квадрат ещё проходит впритык, но именно этот размен от кандидата и хотят услышать.
