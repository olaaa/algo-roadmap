# 169. Majority Element

*Мажоритарный элемент (дословно: элемент большинства)*

**Сложность:** Easy · **Паттерн:** счётчик частот, follow-up — голосование Бойера—Мура · **Классы:** `block03_hashtables.MajorityElement`, `block03_hashtables.MajorityElementNotGuaranteed`

## Условие

Дан массив целых чисел `nums` длины `n`. Найти **мажоритарный элемент** — тот, который встречается **строго больше** `⌊n/2⌋` раз.

Гарантируется, что такой элемент в массиве есть и он единственный. Проверять его отсутствие не нужно.

Обрати внимание на «строго больше половины», а не «чаще всех». Это разные условия, и именно на первом держится весь алгоритм из follow-up.

## Примеры

### Пример 1

```
Вход:  nums = [3, 2, 3]
Выход: 3
```

Длина 3, порог `⌊3/2⌋ = 1`. Тройка встречается 2 раза, это больше единицы.

### Пример 2

```
Вход:  nums = [2, 2, 1, 1, 1, 2, 2]
Выход: 2
```

Длина 7, порог `⌊7/2⌋ = 3`. Двойка встречается 4 раза, единица — 3. Обрати внимание: единица встречается ровно `⌊n/2⌋` раз и мажоритарной **не** является.

### Пример 3

```
Вход:  nums = [1]
Выход: 1
```

Единственный элемент всегда мажоритарный: порог `⌊1/2⌋ = 0`.

## Ограничения

- `n == nums.length`
- `1 <= n <= 5 * 10^4`
- `-10^9 <= nums[i] <= 10^9`
- мажоритарный элемент существует и единственен

## Follow-up из условия

На LeetCode у задачи есть дополнительный вопрос, и он вшит в текст: решить за `O(n)` времени и `O(1)` **дополнительной памяти**.

Первое требование закрывает и обычный счётчик в хеш-таблице. Второе — нет: таблица хранит до `n` записей. Ради `O(1)` и нужен отдельный алгоритм.

## Идея решения

### Способ 1: счётчик частот

Прямое применение приёма блока. Проходим массив, копим в `HashMap` частоты, попутно запоминаем значение с наибольшим счётчиком.

```java
Map<Integer, Integer> counts = new HashMap<>();
int best = nums[0];
for (int value : nums) {
    int count = counts.merge(value, 1, Integer::sum);
    if (count > counts.get(best)) {
        best = value;
    }
}
return best;
```

`merge(value, 1, Integer::sum)` кладёт единицу, если ключа не было, и прибавляет её к существующему значению, если был. Возвращает новое значение — поэтому отдельный `get` после вставки не нужен.

Порог `n/2` тут проверять не требуется: по условию мажоритарный элемент существует, значит самый частый и есть ответ.

`O(n)` времени, `O(n)` памяти. Follow-up не закрыт.

### Способ 2: голосование Бойера—Мура

Алгоритм, ради которого задача и существует. Держим две переменные: `majorityCandidate` — элемент, претендующий на роль мажоритарного, и `survivingVotes` — сколько голосов за него пережило взаимные выбывания.

```java
int majorityCandidate = 0;
int survivingVotes = 0;
for (int vote : nums) {
    if (survivingVotes == 0) {
        majorityCandidate = vote;
    }
    if (vote == majorityCandidate) {
        survivingVotes++;
    } else {
        survivingVotes--;
    }
}
return majorityCandidate;
```

Три правила, и всё:

1. выживших голосов не осталось — выдвигаем текущий элемент новым кандидатом;
2. элемент равен кандидату — голос добавляется;
3. не равен — выбивает один голос за кандидата.

`O(n)` времени, `O(1)` памяти. Follow-up закрыт.

Алгоритм и структура кода из книги: развёрнутый `if/else` и инициализация нулём вместо `nums[0]` — оттуда. Имена переменных свои, в книге стоят `majority`, `count` и `n`:

| в книге | здесь | почему |
|---|---|---|
| `majority` | `majorityCandidate` | прилагательное без существительного; переменная хранит именно кандидата |
| `count` | `survivingVotes` | «count» звучит как «просто считаем», а величина и растёт, и падает |
| `n` | `vote` | перебираются голоса, а не абстрактные значения |


### Почему `survivingVotes`, а не другое английское слово

Русское «непогашенные голоса» переводится несколькими способами, и они не равноценны.

| Слово | Буквально | Как читается носителем |
|---|---|---|
| `unmatched` | не нашедшие пары | стандартный термин в алгоритмах: `unmatched parentheses`, `unmatched elements` |
| `unpaired` | не спаренные | ещё буквальнее про пары, но суше и реже |
| `uncancelled` | не аннулированные | грамматично, но редкое слово; живёт глагол `cancel out`, не прилагательное |
| `surviving` | выжившие | точно ложится на метафору взаимного выбывания |
| `outstanding` | непогашенные | **ложный друг**, см. ниже |

**Про `outstanding`.** Это самый дословный перевод слова «непогашенный»: непогашенный кредит — `outstanding loan`, непогашенный долг — `outstanding debt`. Но в контексте выборов `outstanding votes` по-английски означает **«ещё не подсчитанные голоса»** — совсем другой смысл. В задаче, построенной на метафоре выборов, такое имя сбивало бы с толку сильнее, чем помогало.

**Что выбрано и почему.** `unmatched` — самый нейтральный и привычный для алгоритмических текстов вариант, его стоит знать. `surviving` выбрано потому, что переменная описывается через модель взаимного выбывания, и «выжившие голоса» держат эту картинку прямо в имени.

Общий вывод на будущее: при переводе имени переменной с русского проверять не только словарное соответствие, но и то, какие ассоциации слово тянет в предметной области задачи.

Начальный ноль лучше, чем `nums[0]`: на пустом массиве второй вариант падает с `ArrayIndexOutOfBoundsException`, а этот спокойно доходит до конца цикла, который просто не начинается. По ограничениям задачи пустого входа не бывает, но опираться на существование нулевого элемента там, где без этого можно обойтись, незачем.

### Откуда взялись эти названия

Алгоритм придумали Роберт Бойер и Джей Стротер Мур в 1981 году, и формулировали они его как **задачу о выборах**. Отсюда все термины, и они не метафора, а прямое описание исходной постановки.

**Мажоритарная избирательная система** — та, где для победы нужно абсолютное большинство, больше половины голосов. Не «больше всех», а именно больше половины. Отсюда и название задачи, и требование «строго больше `n/2`».

**Элемент массива** — один поданный голос. Массив `[2,2,1,1,1,2,2]` это бюллетени: два голоса за двойку, три за единицу, два за двойку.

**`majorityCandidate`** — тот, кого мы сейчас считаем возможным победителем.

**`survivingVotes`** — сколько голосов за него пережило взаимные выбывания.

### Почему голосование работает

Представь, что избиратели стоят в очереди и **попарно выбивают друг друга**: подходит человек с чужим бюллетенем — он и один сторонник текущего кандидата взаимно уходят. `survivingVotes` это сколько сторонников кандидата ещё стоит на площади.

Выживших не осталось — кандидат выбыл. Следующий человек в очереди выдвигает кандидатом себя.

Прогон на `[2, 2, 1, 1, 1, 2, 2]`:

| шаг | голос | что происходит | `majorityCandidate` | `survivingVotes` |
|---|---|---|---|---|
| 0 | 2 | выживших нет, двойка выдвигается кандидатом | 2 | 1 |
| 1 | 2 | свой, встаёт рядом | 2 | 2 |
| 2 | 1 | чужой, выбивает одного | 2 | 1 |
| 3 | 1 | чужой, выбивает последнего | 2 | 0 |
| 4 | 1 | выживших нет, единица выдвигается кандидатом | 1 | 1 |
| 5 | 2 | чужой, выбивает | 1 | 0 |
| 6 | 2 | выживших нет, двойка выдвигается кандидатом | 2 | 1 |

Ответ — двойка.

Почему это обязано сработать: каждое выбивание уносит одного своего и одного чужого. Мажоритарный элемент занимает строго больше половины массива — значит чужих меньше, чем его. Даже если каждый чужой заберёт с собой одного сторонника большинства, чужие кончатся раньше. Хотя бы один сторонник большинства останется стоять, и в конце кандидатом окажется он.

Отсюда видно, почему условие «строго больше половины» принципиально. На массиве `[1, 1, 2, 2]` большинства нет вовсе, стороны сокращают друг друга полностью, и алгоритм вернёт какое-то значение — но оно ничего не будет означать.

**Значение `majorityCandidate` по ходу цикла ответом быть не обязано.** Промежуточные значения могут быть любыми, гарантия относится только к состоянию после последней итерации. Это самая частая ошибка при чтении алгоритма.

### Когда большинства может не быть

Отдельный класс `MajorityElementNotGuaranteed`.

Гарантия «элемент точно есть» — не свойство алгоритма, а строчка в условии. Стоит её убрать, и одного прохода становится недостаточно: голосование возвращает кандидата **всегда**, в том числе на массиве, где большинства нет вовсе.

```java
int findMajorityElement(int[] nums) {
    int candidate = majorityElementByVoting(nums);
    return isMajority(nums, candidate) ? candidate : -1;
}
```

Второй проход просто пересчитывает вхождения кандидата и сравнивает с `nums.length / 2`. Неравенство строгое: ровно половина большинством не считается.

Сложность не меняется. Два линейных прохода это по-прежнему `O(n)` времени, а хранятся всё те же две переменные — `O(1)` памяти.

Разница видна прямо: на `[1, 2, 3]` версия с проверкой возвращает `-1`, а версия для LeetCode — какое-то значение, которое ничего не означает. Обе правы, просто у второй в условии есть гарантия, на которую она опирается.

Держать в голове стоит обе. На собеседовании гарантия может как прозвучать в условии, так и не прозвучать — и уточнить это стоит **до** того, как писать код.

## Сложность

| | счётчик частот | голосование Бойера—Мура |
|---|---|---|
| Время | `O(n)` | `O(n)` |
| Память | `O(n)` | `O(1)` |
| Проходов по данным | один | один |
| Что хранит | до `n` записей в таблице | две переменные |
| Follow-up закрыт | нет | да |

Есть и третий способ, без кода: отсортировать массив и взять `nums[n / 2]`. Мажоритарный элемент занимает больше половины, поэтому середина обязана попасть в его блок. Решение в одну строку, но `O(n log n)` времени — назвать на собеседовании стоит, сдавать нет.
