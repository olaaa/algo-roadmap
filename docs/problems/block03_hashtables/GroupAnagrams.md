# 49. Group Anagrams

*Группировка анаграмм (дословно: сгруппировать анаграммы)*

**Сложность:** Medium · **Паттерн:** группировка по ключу · **Класс:** `block03_hashtables.GroupAnagrams`

## Условие

Дан массив строк `strs`. Сгруппировать вместе те строки, которые являются анаграммами друг друга, и вернуть список групп.

Анаграмма — строка из тех же букв в том же количестве, но, как правило, в другом порядке. Строка считается анаграммой самой себя.

Порядок групп в ответе и порядок строк внутри группы не важен.

Это первая задача блока сложности Medium. Отличие от Easy тут не в идее — идея та же хеш-таблица, — а в том, что надо **придумать ключ**, а не получить его готовым.

## Примеры

### Пример 1

```
Вход:  ["eat", "tea", "tan", "ate", "nat", "bat"]
Выход: [["eat", "tea", "ate"], ["tan", "nat"], ["bat"]]
```

Три группы: `eat/tea/ate` из букв `aet`, `tan/nat` из букв `ant`, и одинокая `bat`.

### Пример 2

```
Вход:  [""]
Выход: [[""]]
```

Пустая строка — валидный вход, она образует свою группу из одного элемента.

### Пример 3

```
Вход:  ["a"]
Выход: [["a"]]
```

### Пример 4

```
Вход:  ["ab", "ba", "abc"]
Выход: [["ab", "ba"], ["abc"]]
```

Разная длина — разные группы, даже если буквы пересекаются.

## Ограничения

- `1 <= strs.length <= 10^4`
- `0 <= strs[i].length <= 100`
- `strs[i]` состоит только из строчных латинских букв

Длина строки может быть **нулевой** — про этот случай легко забыть.

## Почему такие ограничения

`10^4` строк по `100` символов — попарное сравнение всех со всеми дало бы `10^8` сравнений анаграмм, каждое из которых само по себе не бесплатное. Это и отсекает наивное решение.

Строчная латиница снова позволяет считать буквы массивом `int[26]` — как в [`ValidAnagram`](../block02_strings_stack/ValidAnagram.md).

## Идея решения

Ключевое наблюдение: **анаграммы неразличимы по составу букв**. Значит нужен «отпечаток» строки — величина, одинаковая у всех анаграмм и разная у не-анаграмм. Тогда задача сводится к раскладыванию строк по корзинам: одинаковый отпечаток — одна корзина.

Это форма «группировка по ключу» из [`Pattern_HashMap.md`](Pattern_HashMap.md): таблица `ключ -> список элементов`.

```java
Map<String, List<String>> groups = new HashMap<>();
for (String word : strs) {
    String key = makeKey(word);
    groups.computeIfAbsent(key, absent -> new ArrayList<>()).add(word);
}
return new ArrayList<>(groups.values());
```

`computeIfAbsent` создаёт список только тогда, когда ключ встретился впервые. Без него понадобилась бы проверка `containsKey` и ручное создание списка.

### Что делает каждая переменная

| Переменная | Что хранит | Зачем она нужна |
|---|---|---|
| `strs` | вход, массив слов | только читается; порядок слов внутри группы наследуется именно от него |
| `groups` | карту «ключ-отпечаток → список слов с этим отпечатком» | сердце решения. Ключ — отпечаток, а не само слово: слова в группе разные, общее у них только он |
| `word` | текущее слово | переменная цикла `for-each`; кладётся в список КАК ЕСТЬ, в исходном виде — ответ состоит из оригиналов, а не из ключей |
| `key` | отпечаток текущего слова | то, по чему слова сходятся в одну корзину |
| `letters` | буквы слова отдельным массивом (способ 1) | копия: строку в Java отсортировать на месте нельзя, а сортировать надо, потому что отпечаток здесь — отсортированные буквы |
| `letterCounts` | 26 счётчиков букв слова (способ 2) | промежуточная сводка, из которой собирается ключ; наружу она не отдаётся и живёт только внутри `buildFrequencyKey` |
| `key` внутри `buildFrequencyKey` (способ 2) | `StringBuilder`, в котором собирается отпечаток | счётчики склеиваются в него через разделитель `#`; зачем разделитель — разбор ниже, в описании способа 2 |
| `absentKey` | ключ, переданный в лямбду `computeIfAbsent` | параметр не используется — список создаётся пустым независимо от ключа. Имя `absentKey` объясняет, что лямбда срабатывает только при отсутствующем ключе |

Отдельно стоит заметить, чего в решении НЕТ: списка ключей, счётчика групп, множества уже виденных слов. Всё это заменяет одна карта — она и группирует, и отвечает на вопрос «была ли такая группа».

### Способ 1: отсортированные буквы как ключ

Отсортировать буквы слова — у анаграмм результат совпадёт.

```
"eat" -> "aet"
"tea" -> "aet"
"tan" -> "ant"
```

```java
char[] letters = word.toCharArray();
Arrays.sort(letters);
String key = new String(letters);
```

Пишется в три строки, объясняется одной фразой. Цена — сортировка каждой строки: `O(k log k)`, где `k` — её длина.

### Способ 2: вектор частот как ключ

Посчитать, сколько раз встречается каждая буква, и склеить счётчики в строку.

```
"eat" -> [1,0,0,0,1,0,...,1,0,...] -> "1#0#0#0#1#..."
```

```java
int[] letterCounts = new int[26];
for (int index = 0; index < word.length(); index++) {
    letterCounts[word.charAt(index) - 'a']++;
}
StringBuilder key = new StringBuilder();
for (int count : letterCounts) {
    key.append(count).append('#');
}
```

Быстрее по времени — `O(k)` вместо `O(k log k)`, — но ключ получается длиннее и код многословнее.

**Разделитель `#` обязателен.** Без него счётчики склеиваются в неоднозначную строку: слово с одной буквой `a` и одиннадцатью `b` даст `111...`, и слово с одиннадцатью `a` и одной `b` — тоже. Разные слова получили бы один ключ, и группы слились бы.

Это приём 7 из [`heuristics.md`](../../heuristics.md): построил ключ-отпечаток — сразу придумай два разных элемента, которые могли бы дать одинаковый ключ. На тестах вида `["eat", "tea"]` склейка не всплывает вовсе — чтобы её поймать, счётчик должен перевалить за десять.

### Какой способ называть на собеседовании

Начать с сортировки: короче и очевиднее. Затем сказать, что ключ можно строить за `O(k)` вектором частот, и что выигрыш заметен только на длинных строках. Здесь `k <= 100`, то есть `log k` меньше семи — разница невелика.

### Про `computeIfAbsent`

```java
groups.computeIfAbsent(key, absent -> new ArrayList<>()).add(word);
```

Метод возвращает значение по ключу, а если ключа нет — сначала вычисляет его функцией, кладёт в карту и возвращает. То есть строка выше делает три вещи: находит или создаёт список, кладёт его в карту при необходимости, и возвращает для добавления слова.

Функция вызывается **только при отсутствии ключа**, поэтому лишних `ArrayList` не создаётся.

## Как сравнить результат с ожиданием

Порядок групп в ответе и порядок слов внутри группы по условию не важны. Значит сравнивать результат с ожиданием напрямую нельзя: группы приходят из `HashMap`, а её порядок обхода зависит от хешей ключей и спецификацией не определён. Тест падал бы на верном ответе.

Поэтому обе стороны сначала приводятся к каноническому виду — метод `normalize`:

```java
copy.sort(Comparator.comparing(group -> String.join(",", group)));
```

```
до:    [[eat, tea, ate], [bat], [tan, nat]]
после: [[ate, eat, tea], [bat], [nat, tan]]
```

Два шага: слова внутри каждой группы сортируются по алфавиту, затем сортируются сами группы.

Второй шаг интереснее первого. Написать `copy.sort(Comparator.naturalOrder())` нельзя — `List` не реализует `Comparable`, естественного порядка у списков нет:

```
error: incompatible types: inference variable T has incompatible bounds
    upper bounds: Comparable<? super T>
    lower bounds: List<String>
```

Поэтому порядок задаётся снаружи, через **ключ сравнения**: каждая группа склеивается в строку, и сравниваются уже строки, у которых естественный порядок есть.

Тема `Comparable` против `Comparator` — частый вопрос на собеседовании сам по себе. Полный разбор: [`docs/java/ComparableAndComparator.md`](../../java/ComparableAndComparator.md).

## Свойства решений

Обозначим `n` — количество строк, `k` — максимальная длина строки.

| Характеристика | Ключ сортировкой | Ключ вектором частот |
|---|---|---|
| Время | `O(n · k log k)` | `O(n · k)` |
| Память | `O(n · k)` — в карте все исходные строки плюс ключи | `O(n · k)`, там же |
| Длина ключа | `k` | до 52 символов при 26 буквах |
| Строк кода | 3 | 8 |
| Проходов по входу | один по списку строк, внутри — обработка каждой строки | один, там же |
| Ранний выход | нет и быть не может: ответ включает все строки, значит каждую надо обработать |
| Изменяет ли вход | нет: сортируется копия символов строки, сам список не трогается | нет |
| Требования к входу | любые строки | только строчные латинские буквы: индекс в векторе частот считается как `символ - 'a'` |
| Порядок групп в ответе | не гарантирован: он определяется обходом `HashMap`. Порядок строк ВНУТРИ группы сохраняется — они добавляются в порядке чтения | то же |
| Детерминированность | да, случайности нет; неупорядоченность ответа — не случайность, а отсутствие гарантий у структуры | да |
| Устойчивость к деградации | `O(1)` у `HashMap` — амортизированная оценка, при массовых коллизиях деградирует | то же |
| Риск склейки ключей | нет: отсортированная строка однозначна | есть, если писать вектор без разделителя — [приём 7 из шпаргалки](../../heuristics.md) |

Наивное решение для сравнения — сравнивать каждую строку с каждой: `O(n² · k)`.

## Опора в книге

Задача 10.2 «Группировка анаграмм» из главы «Сортировка и поиск» (Часть IX «Вопросы собеседования», с. 145 / Часть X «Решения», с. 415). В книге разобраны оба подхода: сортировка массива с компаратором, сравнивающим отсортированные версии строк, и хеш-таблица со списками. Поиск в RAG-файле: фраза «анаграммы группируются друг за другом».

Формулировка там мягче: требуется, чтобы анаграммы стояли **рядом** в отсортированном массиве, а не были разложены по спискам. Хеш-таблица закрывает и её.
