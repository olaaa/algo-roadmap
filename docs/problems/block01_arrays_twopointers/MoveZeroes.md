# 283. Move Zeroes
*Перемещение нулей (дословно: перемести нули)*

**Сложность:** Easy · **Паттерн:** два указателя (чтение и запись) · **Класс:** `block01_arrays_twopointers.MoveZeroes`

## Условие

Дан целочисленный массив `nums`. Нужно перенести все нули в конец массива, сохранив **относительный порядок** остальных элементов.

> **Относительный порядок сохранён** — значит ненулевые элементы идут друг за другом в том же порядке, в каком они стояли в исходном массиве. Для входа `[0, 7, 0, 0, 3, 1]` ответ `[7, 3, 1, 0, 0, 0]`, а не `[1, 3, 7, 0, 0, 0]` — хотя во втором варианте нули тоже в конце.

Изменять массив нужно **на месте** (in-place): нельзя завести второй массив и собрать ответ в нём.

## Примеры

### Пример 1

```
Вход:  nums = [0, 1, 0, 3, 12]
Выход: [1, 3, 12, 0, 0]
```

Ненулевые `1, 3, 12` сдвинулись влево в исходном порядке, два нуля ушли в конец.

### Пример 2

```
Вход:  nums = [0]
Выход: [0]
```

Двигать нечего.

### Пример 3

```
Вход:  nums = [1, 2, 3]
Выход: [1, 2, 3]
```

Нулей нет — массив остаётся без изменений.

## Ограничения

- `1 <= nums.length <= 10^4`
- `-2^31 <= nums[i] <= 2^31 - 1`
- Требуется решение in-place, без копии массива; желательно минимизировать число операций записи.

## Идея решения

Наивно — идти по массиву и при встрече нуля искать справа ближайший ненулевой элемент, меняя их местами. Это `O(n²)`: на каждый ноль отдельный проход по остатку массива. Реализация лежит рядом с эталонной, метод `moveZeroesSwapping`.

Порядок ненулевых при этом сохраняется именно потому, что берётся **ближайший** справа: между собой они никогда не переставляются.

Полезно заметить, в чём именно наивная версия расточительна: внутренний поиск каждый раз начинается заново, хотя всё левее уже просмотрено. Если разрешить ему продолжаться с прошлого места, получится ровно решение двумя указателями ниже — то есть оптимальный вариант выводится из наивного одной правкой.

Вместо этого держим два индекса, оба идут слева направо.

### Что делает каждая переменная

| Переменная | Что хранит | Зачем она нужна |
|---|---|---|
| `nums` | вход и одновременно результат | метод ничего не возвращает: условие требует работы на месте |
| `readIndex` | позицию просматриваемого элемента | просматривает ВСЕ элементы подряд и сдвигается на каждом шаге — это донор, он обязан дойти до конца массива |
| `writeIndex` | позицию, куда ляжет следующий ненулевой элемент | сдвигается ТОЛЬКО после записи, поэтому отстаёт ровно на число пропущенных нулей; после первого прохода служит ещё и границей хвоста |

Разница ролей у двух индексов и есть весь приём: если бы оба сдвигались одинаково, они бы слились в один и переносить было бы нечего. «Долг» между ними — это и есть накопленные нули.

В соседних методах класса набор чуть другой. В однопроходном `moveZeroesOnePass` добавляется `temp`: там элементы не копируются, а меняются местами, и без третьей переменной обмен невозможен. В наивном `moveZeroesSwapping` индексов тоже два, но роли у них иные — `currentIndex` стоит на найденном нуле, а `searchIndex` бегает вправо в поисках ближайшего ненулевого; временная переменная там не нужна, потому что одно из двух значений заведомо ноль, то есть известная константа.

Первый проход: если `nums[readIndex] != 0`, копируем значение в `nums[writeIndex]` и сдвигаем `writeIndex`. Если ноль — просто пропускаем, и между указателями копится «долг» ровно из числа пропущенных нулей.

Здесь стоит добавить проверку `if (writeIndex != readIndex)` перед записью. Пока ни одного нуля не встретилось, указатели идут вровень, и копирование означает «положить элемент туда, где он и так лежит» — холостая запись. На массиве без нулей таких записей будет ровно `n`, то есть весь первый проход отработает вхолостую, но с изменением памяти. Условие их отсекает, и это прямой ответ на требование «минимизировать число операций записи» из ограничений.

Второй проход: после первого цикла `writeIndex` указывает на первую позицию за последним ненулевым элементом. Всё, что правее (включая её) — это места, освободившиеся от пропущенных нулей; забиваем их нулями до конца массива.

Ключевой инвариант **этой задачи**: в момент записи `writeIndex <= readIndex`. Поэтому запись в `nums[writeIndex]` не может затереть ещё не прочитанное значение — читающий указатель либо впереди, либо на той же позиции (тогда элемент копируется сам в себя).

Оговорка «в момент записи» существенна: сразу после `writeIndex++` пишущий индекс на мгновение равен `readIndex + 1`, но тут же итерация заканчивается и `readIndex` тоже увеличивается. Устойчивая формулировка через счётчики: записано всегда не больше, чем просмотрено, а разница — это ровно количество пропущенных нулей.

### Кто впереди — read или write: общего правила нет

Из формулы `writeIndex <= readIndex` легко сделать неверный вывод, будто пишущий указатель всегда плетётся за читающим. Это свойство **конкретной задачи**, а не приёма «чтение и запись».

Контрпример лежит в этом же блоке. В [`MergeSortedArray`](MergeSortedArray.md) запись идёт **с конца**: `writeIndex` стартует с последней позиции `nums1` и оказывается **впереди** обоих читающих указателей, а движутся все трое справа налево. Инвариант там зеркальный: `writeIndex >= firstIndex`, и именно поэтому запись в хвост безопасна — слева ещё не прочитанные данные, справа уже свободное место.

| Задача | Направление обхода | Где пишущий | Инвариант |
|--------|--------------------|-------------|-----------|
| `MoveZeroes` | слева направо | позади читающего | `writeIndex <= readIndex` |
| `MergeSortedArray` | справа налево | впереди читающих | `writeIndex >= firstIndex` |

Общее у обеих задач одно, и формулировать надо именно это: **пишущий указатель не должен заходить на территорию, которую ещё предстоит прочитать.** Куда при этом смотрит неравенство — следствие того, с какого конца идёт обход и где лежит свободное место.

На собеседовании это стоит проговаривать так: «свободное место здесь накапливается слева/справа, поэтому пишу с той стороны, и запись гарантированно не задевает непрочитанное». Заученное `write <= read` на задаче со слиянием собьёт с толку.

Ещё одно отличие, которое видно только после цикла: у `moveZeroes` второй цикл доводит `writeIndex` до конца массива, поэтому финальное значение теряется. У однопроходного варианта ниже `writeIndex` останавливается на количестве ненулевых элементов — это готовая граница между данными и нулями, и в родственной задаче «Remove Element» именно её и просят вернуть.

### Вариант в один проход (через обмен)

Вместо копирования с досыпкой нулей можно на каждом ненулевом элементе делать `swap(nums[writeIndex], nums[readIndex])`. Тогда нули «всплывают» вправо сами и второй цикл не нужен. Реализация — метод `moveZeroesOnePass`.

Почему обмен корректен: все позиции между `writeIndex` и `readIndex` — это ровно пропущенные нули, поэтому в `nums[writeIndex]` в момент обмена заведомо лежит ноль. Обмен ставит ненулевой элемент на своё место, а ноль уезжает туда, откуда элемент забрали.

Проверка `writeIndex != readIndex` нужна и здесь, причём даже сильнее: без неё элемент менялся бы сам с собой, а это три операции вместо нуля.

Сложность та же, `O(n)` времени и `O(1)` памяти. Разница — в числе записей: обмен пишет **две** ячейки на каждый ненулевой элемент, тогда как основной вариант — одну на элемент плюс по одной на каждый ноль. На массиве с малым числом нулей выгоднее основной вариант, на массиве, где нулей много, разрыв сокращается.

### Какую версию вести на собеседовании

Вести **двухпроходную** — ту, что выше. Причины по убыванию важности:

1. Её проще объяснить. Каждый цикл делает одно понятное дело: первый переносит ненулевые влево, второй забивает хвост нулями. У однопроходной приходится держать в голове инвариант средней зоны, чтобы обосновать, почему обмен безопасен, — а интервьюер почти наверняка спросит именно «почему это работает».
2. Она не хуже по существу: та же сложность, а по числу записей даже экономнее.

Однопроходную упоминать как альтернативу: «можно в один проход через обмен, но тогда на каждый ненулевой элемент приходится две записи вместо одной». Этого достаточно, чтобы показать, что развилку видишь, и при этом не пришлось защищать более сложное рассуждение под давлением.

Общее правило: уверенный разбор простого решения ценится выше, чем заминка на хитром.

### Отличие от `MergeSortedArray`

Обе задачи из подвида «однонаправленное движение», но формы разные. Здесь **одна** коллекция и роли «читает / пишет»; в `MergeSortedArray` — **две** коллекции, по указателю чтения на каждую, плюс отдельный указатель записи. Подробнее — в `Pattern_TwoPointers.md`.

Второе отличие, про направление обхода и положение пишущего указателя, разобрано выше в разделе «Кто впереди — read или write».

## Свойства решения

| Характеристика | Значение |
|---|---|
| Время | `O(n)` — два прохода подряд, каждый элемент посещается не больше двух раз |
| Память | `O(1)` — два индекса, копии массива нет |
| Проходов по входу | два: первый уплотняет ненулевые элементы, второй досыпает нули в хвост |
| Число записей | ровно столько, сколько нужно: в первом проходе запись пропускается, когда указатели идут вровень, — иначе элемент копировался бы сам в себя |
| Ранний выход | нет: чтобы узнать, есть ли ненулевые элементы дальше, массив надо досмотреть до конца |
| Изменяет ли вход | да, это требование условия — работа на месте |
| Требования к входу | никаких: порядок и значения произвольны |
| Устойчивость (stability) | сохраняется: относительный порядок ненулевых элементов не меняется, и это тоже требование условия |
| Работа на потоке | первый проход по природе потоковый, но второй требует знать, где массив кончился |
| Детерминированность | да |
| Завершаемость | оба цикла идут по возрастающему индексу до длины массива |
| Вырожденные входы | массив без нулей — второй цикл не начинается; массив из одних нулей — первый цикл не делает ни одной записи |

Альтернатива для сравнения — однопроходный вариант с обменом: проходов один, но записей вдвое больше (обмен — это две записи против одной). Разбор развилки выше, в разделе про число операций записи.
