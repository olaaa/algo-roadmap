# 643. Maximum Average Subarray I

*Максимальное среднее подмассива (дословно: максимальное среднее подмассива I)*

**Сложность:** Easy · **Паттерн:** скользящее окно фиксированной ширины · **Класс:** `block04_sliding_window.MaxAverageSubarray`

## Условие

Дан массив целых чисел `nums` и целое число `k`. Найти **непрерывный подмассив длины ровно `k`** с максимальным средним арифметическим и вернуть это среднее.

Ответ принимается с погрешностью до `10^-5`.

Подмассив непрерывный — элементы идут подряд, без пропусков. Длина фиксирована: не «не больше `k`», а ровно `k`.

## Примеры

### Пример 1

```
Вход:  nums = [1, 12, -5, -6, 50, 3], k = 4
Выход: 12.75
```

Лучшее окно — `[-5, -6, 50, 3]`, сумма 42, среднее `42 / 4 = 12.75`. Обрати внимание, что в нём есть два отрицательных числа: жадный выбор «взять самые большие» тут не работает, элементы обязаны идти подряд.

### Пример 2

```
Вход:  nums = [5], k = 1
Выход: 5.00000
```

### Пример 3

```
Вход:  nums = [0, 4, 0, 3, 2], k = 1
Выход: 4.0
```

При `k = 1` задача вырождается в поиск максимального элемента.

### Пример 4

```
Вход:  nums = [-1, -2, -3], k = 2
Выход: -1.5
```

Все числа отрицательные, ответ тоже отрицательный. Инициализировать максимум нулём нельзя.

## Ограничения

- `n == nums.length`
- `1 <= k <= n <= 10^5`
- `-10^4 <= nums[i] <= 10^4`

Обрати внимание: `k <= n` гарантировано, то есть окно заведомо помещается в массив. Проверять это не нужно.

## Почему такие ограничения

`10^5` элементов отсекают наивное решение: перебрать все `n - k + 1` окон и каждое просуммировать заново — это `O(n · k)`, в худшем случае порядка `10^10` операций.

Диапазон значений важен для выбора типа суммы, см. ниже.

## Идея решения

Соседние окна отличаются ровно двумя элементами: один вышел слева, один вошёл справа. Значит сумму не надо считать заново — её достаточно поправить на разницу.

**Первый шаг.** Складываем первые `k` элементов — это сумма стартового окна.

**Дальше.** Двигаем окно на одну позицию вправо: прибавляем вошедший элемент, вычитаем вышедший, сравниваем с лучшим результатом.

```java
int windowSum = 0;
for (int windowEnd = 0; windowEnd < k; windowEnd++) {
    windowSum += nums[windowEnd];
}

int maxSum = windowSum;
for (int windowEnd = k; windowEnd < nums.length; windowEnd++) {
    int leavingIndex = windowEnd - k;
    windowSum = windowSum + nums[windowEnd] - nums[leavingIndex];
    maxSum = Math.max(maxSum, windowSum);
}

return (double) maxSum / k;
```

Индекс в обоих циклах назван одинаково — `windowEnd`, и это не небрежность. В первом цикле окно занимает позиции `[0..windowEnd]`, то есть индекс двигает его правую границу; во втором она же едет дальше, только окно перестало расти и поехало целиком. Разными циклы делает не роль индекса, а тело: в первом сумма только прибавляется, во втором ещё и вычитается.

Второй индекс, `leavingIndex`, — позиция элемента, который окно покидает. С такими именами строка читается как «сумма плюс вошедший, минус уходящий», и пояснять её отдельным комментарием не нужно.

Про имя `leavingIndex` стоит сказать отдельно, потому что напрашивается `windowStart` — и это была бы ошибка. Начало текущего окна находится на `windowEnd - k + 1`, а `windowEnd - k` — позиция уже вне окна, начало ПРЕДЫДУЩЕГО окна. Имя `windowStart` обещало бы левую границу и провоцировало бы поправку на единицу там, где её быть не должно.

Про сам приём — [`Pattern_SlidingWindow.md`](Pattern_SlidingWindow.md), подвид «окно фиксированной ширины».

### Кто вошёл и кто вышел

Самое частое место для ошибки — индекс уходящего элемента.

Когда правая граница стоит на `windowEnd`, окно занимает позиции с `windowEnd - k + 1` по `windowEnd` включительно. Значит на прошлом шаге оно начиналось на `windowEnd - k` — этот элемент и покидает окно, он же в коде назван `leavingIndex`.

Частый вопрос к этой строке: «`windowEnd` ведь только что увеличился, не нужна ли поправка на единицу — `windowEnd - k - 1`?» Не нужна. Увеличение `windowEnd++` срабатывает в КОНЦЕ итерации, поэтому внутри тела цикла `windowEnd` — индекс элемента, который входит прямо сейчас. А `windowEnd - k - 1` указывал бы на элемент, выпавший из окна ещё раньше: на первой же итерации это `-1` и выход за границу массива.

```
nums:          [1, 12, -5, -6, 50, 3]
индексы:        0   1   2   3   4  5
окно k=4:      [1  12  -5  -6]              сумма 2
шаг вперёд:        [12  -5  -6  50]         сумма 2 + 50 − 1 = 51
                    ↑            ↑
              вышел nums[0]   вошёл nums[4]
```

Проверить себя можно на длине окна: `windowEnd - (windowEnd - k + 1) + 1 = k`.

### Максимум ищем по сумме, а не по среднему

Все окна одной длины `k`, поэтому делить на `k` можно **один раз в конце**. Так короче, точнее и быстрее: деление выполняется однажды, а не на каждой итерации, и не накапливается погрешность вещественной арифметики.

### Ловушка: целочисленное деление

Если написать `return maxSum / k;`, оба операнда будут `int`, и Java выполнит **целочисленное** деление — дробная часть отбросится. На примере 1 вместо `12.75` вернулось бы `12.0`, и метод молча дал бы неверный ответ.

Лечится приведением одного из операндов:

```java
return (double) maxSum / k;
```

Приведение обязано стоять **до** деления. `(double) (maxSum / k)` уже поздно: деление к этому моменту произошло в `int`, и приводить нечего.

Разбор целочисленного деления и усечения — в [`docs/java/Rounding.md`](../../java/Rounding.md).

### Про тип суммы

Максимально возможная сумма окна — `10^5 · 10^4 = 10^9`. Это меньше `Integer.MAX_VALUE ≈ 2.15 · 10^9`, поэтому `int` подходит.

Но запас всего вдвое. Если бы ограничения были чуть шире, сумма переполнилась бы молча и знак поехал бы. На собеседовании стоит сказать вслух, что ограничения перемножены и `int` выбран сознательно, — или сразу взять `long`, что дешевле любых рассуждений. Разбор переполнения — в [`docs/java/Int.md`](../../java/Int.md).

### Почему максимум нельзя инициализировать нулём

Классическая ошибка на массивах, где все числа отрицательные. Начальное значение обязано быть **суммой первого окна**, а не нулём и не `Integer.MIN_VALUE`.

С нулём на входе `[-1, -2, -3], k = 2` ответ получился бы `0.0` вместо `-1.5`.

## Свойства решения

| Характеристика | Значение |
|---|---|
| Время | `O(n)` — два цикла подряд: `k` элементов на первое окно, остальные на сдвиги; лучший и худший случай совпадают |
| Память | `O(1)` — сумма, максимум и индексы |
| Проходов по входу | один: первый цикл набирает окно, второй продолжает с позиции `k`, возвратов назад нет |
| Ранний выход | нет: лучшее окно может оказаться последним, поэтому массив досматривается целиком |
| Изменяет ли вход | нет, массив только читается |
| Требования к входу | `k` в пределах `1..n`; сортировка не нужна и была бы вредна — окно требует исходного порядка |
| Работа на потоке | да по природе: сдвиг требует помнить только `k` последних элементов. Потоковой версии в классе нет |
| Детерминированность | да |
| Устойчивость к деградации | худшего случая нет: на каждом шаге ровно одно сложение и одно вычитание |
| Завершаемость | оба цикла идут по возрастающему индексу до длины массива |
| Точность | максимум ищется по целочисленной сумме, деление на `k` выполняется один раз в конце — погрешность вещественной арифметики не накапливается |

Наивное решение для сравнения — суммировать каждое окно заново: `O(n · k)`, до `10^10` операций на предельном входе.
