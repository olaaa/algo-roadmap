# double — число с плавающей точкой

## Короткий ответ для собеседования

Две фразы, которых хватает в 90% случаев:

> Двоичная дробь не представляет `0.1` точно, потому что знаменатель не степень двойки.
>
> Поэтому деньги хранят в `BigDecimal`, а `double` не сравнивают через `==`.

Ниже — почему это так и что ещё из этого следует.

## Что это

64 бита, 8 байт. Значение хранится как **знак × мантисса × 2^порядок** — то есть это двоичная дробь, а не десятичная.

```
Double.SIZE = 64 бит, BYTES = 8
Double.MAX_VALUE = 1.7976931348623157E308
Double.MIN_VALUE = 4.9E-324        наименьшее положительное, не самое отрицательное
```

Обрати внимание на `MIN_VALUE`: у целочисленных типов это самое отрицательное значение, а у `double` — наименьшее положительное, ближайшее к нулю. Разное значение одного и того же имени.

У `float` вдвое меньше: 32 бита, `MAX_VALUE = 3.4028235E38`. В алгоритмических задачах `float` не используют — точности мало, а выигрыш по памяти неактуален.

## Почему `0.1` не представима точно

Конечной двоичной дробью записываются только числа вида `k / 2^m`. У одной десятой знаменатель `10 = 2 × 5`, и пятёрка ни в какую степень двойки не входит — значит запись бесконечна.

Это та же ситуация, что с `1/3` в десятичной системе: `0.333...` не кончается, потому что тройка не делит никакую степень десяти. Просто мы привыкли к десятичному основанию и не удивляемся.

В битах повторяемость видна прямо:

```
биты 0.1: 11111110111 0011001100110011001100110011001100110011001100110 1010
                       ↑ дальше бесконечно повторяется 0011
```

Мантисса — 52 бита явных плюс один подразумеваемый. Бесконечный хвост обрезается и округляется, поэтому в памяти лежит не одна десятая:

```
0.1  ->  0.1000000000000000055511151231257827021181583404541015625
0.2  ->  0.200000000000000011102230246251565404236316680908203125
0.3  ->  0.299999999999999988897769753748434595763683319091796875
```

`0.1` и `0.2` округлились вверх, `0.3` — вниз. Отсюда классика:

```
0.1 + 0.2 = 0.30000000000000004
0.1 + 0.2 == 0.3  ->  false
```

Сумма двух завышенных значений оказалась больше, чем занижённое `0.3`.

А эти хранятся **точно**, потому что их знаменатели — степени двойки:

```
0.5 = 1/2      0.25 = 1/4      0.75 = 3/4      0.125 = 1/8
```

### Почему на печати всё выглядит нормально

`System.out.println(0.1)` выводит `0.1`. Ловушка именно в этом: печать показывает кратчайшую десятичную запись, которая однозначно опознаёт данное двоичное значение, а не само значение. Увидеть правду можно только специально — `new BigDecimal(0.1)`.

Поэтому ошибку годами не замечают, а потом ловят расхождение в копейку раз в квартал.

## Сравнивать через `==` нельзя

Вместо равенства проверяют, что разность по модулю меньше выбранного порога:

```java
Math.abs(first - second) < 1e-9
```

Порог зависит от задачи: для координат один, для физики другой. «Правильного» эпсилона на все случаи не существует, и на собеседовании стоит это проговорить.

Есть и вторая причина, кроме накопления ошибок: на больших значениях соседние представимые числа расходятся настолько, что прибавление единицы вообще ничего не меняет.

```
1e16 + 1 == 1e16  ->  true
```

## Особые значения

Деление на ноль у `double` не бросает исключение, в отличие от `int`:

```
 1.0 / 0.0 = Infinity
-1.0 / 0.0 = -Infinity
 0.0 / 0.0 = NaN
```

### `NaN` не равен сам себе

```
nan == nan                        ->  false
Double.isNaN(nan)                 ->  true
```

Так требует стандарт IEEE 754: `NaN` означает «не число», и сравнивать его не с чем. Проверять надо через `Double.isNaN`.

Но у обёртки `Double` поведение другое:

```
Double.valueOf(nan).equals(Double.valueOf(nan))  ->  true
HashSet: содержит NaN после add                  ->  true
```

`equals` у обёртки сравнивает **биты**, а не значения, поэтому `NaN` равен `NaN` и нормально живёт в коллекциях. Расхождение между `==` для примитива и `equals` для обёртки — популярный вопрос-ловушка.

### Минус ноль

```
-0.0 == 0.0                                    ->  true
Double.compare(-0.0, 0.0)                      ->  -1
Double.valueOf(-0.0).equals(Double.valueOf(0.0)) -> false
1.0 / -0.0                                     ->  -Infinity
```

Оператор `==` считает нули равными, а `compare` и `equals` — нет, по той же причине: они смотрят на биты. Практическое следствие видно в последней строке: знак нуля сохраняется и влияет на результат деления.

## Деньги

```
double:      0.1 + 0.2 = 0.30000000000000004
BigDecimal:  0.1 + 0.2 = 0.3
```

Для денег берут `BigDecimal` со **строковым** конструктором и явным `RoundingMode` — разбор в [`Rounding.md`](Rounding.md).

Альтернатива, которую тоже стоит назвать: хранить сумму в **минимальных единицах** целым числом. Не рубли дробью, а копейки в `long`. Так делают в биржевых и платёжных системах, где важна скорость: целочисленная арифметика быстрее `BigDecimal` и не требует выбирать режим округления.

## Типичные вопросы на собеседовании

**Почему `0.1 + 0.2 != 0.3`?**
`double` хранит двоичную дробь. Одна десятая в двоичной системе бесконечна, потому что знаменатель `10` содержит пятёрку и не является степенью двойки. Хвост обрезается, `0.1` и `0.2` округляются вверх, `0.3` вниз — сумма оказывается больше.

**Как правильно сравнивать `double`?**
Через модуль разности и порог: `Math.abs(a - b) < eps`. Величина порога зависит от задачи.

**Чему равно `Double.NaN == Double.NaN`?**
`false`, так требует IEEE 754. Проверка — `Double.isNaN`. А вот `Double.valueOf(NaN).equals(...)` даёт `true`, потому что `equals` сравнивает биты.

**Что вернёт `1.0 / 0.0`?**
`Infinity`. Исключения не будет — в отличие от целочисленного деления на ноль, которое бросает `ArithmeticException`.

**Что такое `Double.MIN_VALUE`?**
Наименьшее **положительное** значение, `4.9E-324`, а не самое отрицательное. У целочисленных типов `MIN_VALUE` означает другое.

**Почему деньги нельзя в `double`?**
Ошибки представления накапливаются при суммировании и дают расхождение в копейки. Нужен `BigDecimal` со строковым конструктором либо целое число минимальных единиц.
