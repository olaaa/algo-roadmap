# Comparable и Comparator — как в Java задаётся порядок

## Что это

Два интерфейса, отвечающих на один вопрос: «какой из двух объектов раньше». Разница в том, **где живёт правило сравнения**.

| | `Comparable` | `Comparator` |
|---|---|---|
| Пакет | `java.lang` | `java.util` |
| Метод | `compareTo(other)` | `compare(first, second)` |
| Аргументов | один | два |
| Где правило | внутри самого класса | снаружи, отдельным объектом |
| Сколько может быть | одно на класс | сколько угодно |
| Как называют | естественный порядок | внешний порядок |

`Comparable` — это свойство класса: «объекты этого типа умеют сравниваться между собой». Так устроены `String`, `Integer`, `LocalDate`.

`Comparator` — отдельная стратегия сравнения. Она не требует ничего от самого класса и позволяет иметь несколько разных порядков для одного типа.

Оба метода возвращают `int` по одному соглашению: отрицательное — первый раньше, ноль — равны по этому порядку, положительное — первый позже. Конкретное значение неважно, важен только знак.

```
"apple".compareTo("banana") = -1
"Apple".compareTo("apple")  = -32
```

Второе число — это разность кодов `'A'` (65) и `'a'` (97). Полагаться на саму величину нельзя, только на знак.

## Естественный порядок

У `String` естественный порядок лексикографический, посимвольно по коду. Отсюда следствие, которое регулярно ловят на собеседовании:

```
[banana, Apple, cherry, apple]  →  [Apple, apple, banana, cherry]
```

Заглавные буквы идут раньше строчных, потому что в таблице символов `A` = 65, а `a` = 97. Это не «неправильная сортировка», а прямое следствие естественного порядка. Нужен другой — берётся компаратор, например `String.CASE_INSENSITIVE_ORDER`.

## Когда естественного порядка нет

Ключевой момент, из-за которого компаратор вообще появляется в коде. Не у всякого типа есть `compareTo`. У `List` его нет:

```java
List<List<String>> groups = new ArrayList<>();
groups.sort(Comparator.naturalOrder());
```

```
error: incompatible types: inference variable T has incompatible bounds
    upper bounds: Comparable<? super T>
    lower bounds: List<String>
```

Компилятор говорит буквально: `naturalOrder()` объявлен как `<T extends Comparable<? super T>>`, а `List<String>` этому не удовлетворяет. Значит порядок надо задать снаружи.

## `Comparator.comparing` — сравнение по ключу

Самый частый способ построить компаратор: описать не «как сравнивать объекты», а «что у объекта брать для сравнения».

```java
copy.sort(Comparator.comparing((List<String> group) -> String.join(",", group)));
```

Разбор по частям:

- `group -> String.join(",", group)` — **извлекатель ключа**. Берёт группу `[ate, eat, tea]` и возвращает строку `"ate,eat,tea"`.
- `Comparator.comparing(...)` строит компаратор, который при каждом сравнении вызывает извлекатель для обоих элементов и сравнивает уже **полученные ключи** их естественным порядком.
- Ключ обязан быть `Comparable`. `String` им является — этого и добиваемся.

Что происходит фактически:

```
[nat, tan]        →  "nat,tan"
[bat]             →  "bat"          сравниваются эти строки
[ate, eat, tea]   →  "ate,eat,tea"
```

Результат, проверено запуском:

```
до сортировки   : [[nat, tan], [bat], [ate, eat, tea]]
после сортировки: [[ate, eat, tea], [bat], [nat, tan]]
```

Тип параметра `group` компилятор выводит сам, из типа элементов списка.

### Извлекатель вызывается на каждом сравнении

Не один раз на элемент. Проверено счётчиком: на списке из трёх элементов извлекатель вызвался **4 раза**, то есть по два на каждое сравнение.

Для тестов и мелких списков это неважно. Но если ключ дорогой (склейка строк, разбор даты, обращение к базе), считать его заново на каждом сравнении — это `O(n log n)` вычислений ключа. Тогда ключ считают один раз заранее и сортируют пары «ключ + объект». На собеседовании это хороший ответ на вопрос «а что здесь можно оптимизировать».

## Составные и обратные порядки

Компараторы собираются цепочкой:

```java
people.sort(Comparator.comparingInt(Person::age).thenComparing(Person::name));
```

`thenComparing` подключается только тогда, когда первый компаратор вернул ноль. Проверено запуском:

```
по возрасту, затем по имени: [Борис 25, Анна 30, Ольга 30]
```

Борис первый по возрасту; Анна и Ольга ровесницы, поэтому между собой упорядочены по имени.

`reversed()` разворачивает готовый компаратор:

```java
people.sort(Comparator.comparing(Person::name).reversed());
```

```
[Ольга, Борис, Анна]
```

Полезные фабрики: `comparingInt`, `comparingLong`, `comparingDouble` — то же, что `comparing`, но без упаковки примитива в обёртку. `nullsFirst`/`nullsLast` — оборачивают компаратор так, чтобы `null` не приводил к `NullPointerException`.

## Согласованность с equals

Требование из документации: правило сравнения **желательно** согласовать с `equals`. Согласовано — значит `a.compareTo(b) == 0` тогда и только тогда, когда `a.equals(b)`.

Нарушать это можно, но у `TreeSet` и `TreeMap` будут неожиданные последствия: они опираются на компаратор, а не на `equals`. Проверено запуском:

```java
Set<String> set = new TreeSet<>(String.CASE_INSENSITIVE_ORDER);
set.add("Apple");
set.add("APPLE");   // вернул false
```

```
содержимое: [Apple]
"Apple".equals("APPLE") = false
```

С точки зрения `equals` это две разные строки, а множество считает их одной — потому что компаратор вернул ноль. `HashSet` в той же ситуации хранил бы обе.

## Типичные вопросы на собеседовании

**Чем `Comparable` отличается от `Comparator`?**
`Comparable` — естественный порядок, задан внутри класса, один на тип, метод `compareTo` с одним аргументом. `Comparator` — внешняя стратегия, их может быть много, метод `compare` с двумя аргументами. Если класс чужой и менять его нельзя, остаётся только `Comparator`.

**Что должен возвращать `compareTo`?**
`int`, у которого важен знак: отрицательное — первый раньше, ноль — равны, положительное — первый позже. Величина ничего не значит.

**Почему нельзя сравнивать вычитанием, `return first.hashCode() - second.hashCode()`?**
Разность переполняет `int`, если у чисел **разные знаки** и истинная разность достигает `2^31`. Тогда знак результата становится противоположным правильному, и порядок ломается. `hashCode` — как раз опасный случай: он бывает большим отрицательным.

Если оба значения неотрицательные (или оба неположительные), переполнения не бывает никогда — например, с полем «возраст» вычитание не сломается. Но полагаться на это не стоит: правило про знаки легко забыть при рефакторинге, когда поле начнёт принимать отрицательные значения.

Правильно — `Integer.compare(first, second)` или `Comparator.comparingInt`.

Диапазон, дополнительный код и цифры — [`Int.md`](Int.md), класс-иллюстрация `demo.IntSubtractionOverflow`.

**Как отсортировать по двум полям?**
`Comparator.comparing(...).thenComparing(...)`. Второй компаратор срабатывает, только если первый вернул ноль.

**Что значит «согласован с equals» и когда это важно?**
`compareTo(b) == 0` совпадает с `equals(b)`. Важно для `TreeSet` и `TreeMap`: они решают вопрос о равенстве компаратором, а не `equals`, поэтому при рассогласовании множество может «потерять» элемент, который с точки зрения `equals` уникален.

**Сколько раз вызывается функция в `Comparator.comparing`?**
На каждом сравнении, то есть порядка `n log n` раз, а не по разу на элемент. Если ключ дорогой, его считают заранее.
